### 2026-09-13 — identification, backup, first boot of a non-stock image

**Kernel tree.** Identified `kernel-msm-MMI-QPT30.61-18` as Motorola's Android 10 kernel release: Linux 4.4.192 + Qualcomm CAF + Motorola patches, covering sdm660/sdm636 devices (chef, lake, payton, evert, beckham, heart, flay) and msm8998 (nash, messi). Motorola builds chef with `sdm660_defconfig` concatenated with `ext_config/moto-sdm660-chef.config` (see `defconfig.mk`).

**Device.** Moto One Power, serial `ZF6223WZGL`, running stock `QPTS30.61-18-16-19` (Android 10, patch 2021-10-01, kernel `4.4.192-perf+` built with GCC 4.9 on 2021-09-22 — same line as the source tree). Bootloader `MBM-3.0-chef_retail-06369b83c90-210922`, **already unlocked** (`verifiedbootstate=orange`, `flash.locked=0`). A/B, slot `_a`. Battery health "Good".

**Firmware sources.** Stock firmware for chef is no longer on the usual Moto mirror (lolinet purges after 5 years). The Android Dumps GitLab (`dumps.tadiphone.dev/dumps/motorola/chef_sprout`) has extracted dumps up to `18-16-16`, one branch per build. Decided to dump from the device itself instead (exact version, plus device-unique partitions). See memory note / `stock/`.

**TWRP.** Downloaded official TWRP 3.7.0_9-0 for chef from dl.twrp.me. First two downloads were silently truncated by the server (5 MB and 7.5 MB of a 32 MB file) and failed the published sha256; resuming with `curl -C -` completed it and it verified (`2a632fe9…`).

**The fastboot rabbit hole.** `fastboot boot twrp.img` hung forever at `Sending 'boot.img'`. Short commands (`getvar`) worked; any bulk data transfer stalled, even a 1 MB test file. Killed sends leave the bootloader in a confused state where it processes each new command with the length of the previous longer one (`getvar:all` after `download:…` came back as `all0100000`) — only a Power+VolDown hard reset clears it. Tried: two cables, three ports, disabling USB2 LPM (`echo 0 > …/power/usb2_hardware_lpm`, and `22b8:2e80:k` in `usbcore.quirks`), an older fastboot binary (r33). None helped. **Root cause: the AMD 400-series chipset USB controller** (`02:00.0`, bus 1). Moving the phone to a CPU-attached port (`0c:00.3`, bus 3 — the four blue rear USB 3.1 Gen1 ports on the B450 Steel Legend) fixed it instantly: 31 MB sent in 0.7 s.

**Backup.** Booted TWRP from RAM (nothing flashed), got a root adb shell, and dumped all 77 partitions except userdata with `adb exec-out dd`, verifying each against an on-device `sha256sum`. 11 GB in `stock/partitions/`. Two scripting bugs on the way: TWRP's toybox `dd` rejects `bs=4M` (use `bs=4194304`), and `adb shell` inside a `while read` loop eats the loop's stdin (read from fd 3, redirect adb from `/dev/null`). Also captured the running kernel's dmesg, `/proc/cmdline` and input device list, then rebooted back to stock Android — phone is unchanged.

**Findings from the logs.**
- Panel is detected by the bootloader and named on the cmdline (`mdss_mdp.panel=1:dsi:0:qcom,mdss_dsi_mot_tianma_nt_618_fhd_vid_v0…`); the tree has three chef panel variants (Tianma/NT, Tianma/FT, CSOT/NT) so a replacement display of another variant should still work.
- Touch on this unit is Novatek NT36772 (`NVTCapacitiveTouchScreen`), not Focaltech.
- Modem/ADSP/CDSP/Wi-Fi firmware live in the `modem_a` partition, BT firmware in `bluetooth_a`, DSP in `dsp_a` — Android mounts them at `/vendor/firmware_mnt`, `/vendor/bt_firmware`, `/vendor/dsp`. Our rootfs must do the same. GPU/touch firmware and Wi-Fi config are in `vendor_a` under `/vendor/firmware` and `/vendor/etc/wifi`.
- Stock cmdline includes `skip_initramfs` and `root=/dev/mmcblk0p67`; we drop `skip_initramfs` so the kernel uses our initramfs.
- Wi-Fi and BT MAC addresses are passed on the cmdline.
- **No ANT+**: Motorola didn't enable it (no `com.dsi.ant.server`, no `android.hardware.ant` feature). Sensor plan is BLE via BlueZ; USB ANT+ stick over OTG as fallback for ANT-only sensors.

**Status at end of day.** Nothing on the phone has been modified. Paused pending a replacement display (not a blocker for the next steps — they only need USB networking).

### 2026-09-13 (later) — toolchain

Set up AOSP `aarch64-linux-android-4.9` (branch `android-10.0.0_r47`, "GCC 4.9.x 20150123 (prerelease)" — the same compiler line as the stock kernel banner). Gotchas: in that release `gcc`/`g++` are python2 wrapper scripts that only print a deprecation nag and exec a UUID-named real driver — `scripts/setup-toolchain.sh` replaces them with symlinks to the real binaries. The kernel Makefile hardcodes `PYTHON = python` for `scripts/gcc-wrapper.py` (which is python3-clean) and the tree's bundled dtc defines `yylloc` twice (fails to link under GCC ≥ 10's `-fno-common`); both are handled by command-line overrides in `kmake`. Note the submodule tags `MMI-QPT30.61-18` and `MMI-QPW30.61-21` are the same commit.

**Kernel branch.** The `kernel/` submodule now points at the fork `nshnt-xyz/kernel-msm`, branch `chef-cyclo` (Motorola's tree + our patches). Inside `kernel/`, `origin` is the fork and `upstream` is Motorola.

**First full build.** Two problems. (1) `scripts/gcc-wrapper.py` is *not* python3-clean: its warning path uses py2 `print >>` and, by design, it fails the build on any warning at all; `kmake` now passes `CC=` to bypass it. (2) `arch/arm64/kernel/cpuinfo.c` failed on `system_rev` undeclared — it's guarded by `CONFIG_BOOTINFO`, which lives in `ext_config/moto-sdm660.config`. So the real stack per `defconfig.mk` is **three** files: `sdm660_defconfig` + `moto-sdm660.config` (platform, via `moto-$(DEFCONFIG_BASENAME)`) + `moto-sdm660-chef.config` (device, via `KERNEL_EXTRA_CONFIG`). The chef fragment is clearly a delta on the platform one (it un-sets Madera options the platform enables). The chef fragment turns on `CONFIG_TOUCHSCREEN_NT36xxx`, the Novatek driver our unit needs (the platform fragment has only the Focaltech options; corrected 2026-09-18, an earlier version of this note said platform). With that, `kmake -j12` completes in ~5 min with one harmless host warning (modpost). Output: `Image.gz-dtb` 14.5 MB (Image.gz + `sdm636-chef-evt.dtb` only, thanks to `CONFIG_CHEF_DTB`), `UTS_RELEASE 4.4.192-g6d83ef138`. Stock `boot_a.img` header (v0, 4096-byte pages) carries a 12.4 MB kernel and a 10.4 MB ramdisk.

### 2026-09-13 (later) — initramfs and boot image

**`skip_initramfs` comes from the bootloader, not the boot image.** Neither the stock nor the TWRP boot image header has it; the runtime cmdline TWRP saw does (`… androidboot.slot_suffix=_a skip_initramfs rootwait ro init=/init …`, all appended by the bootloader, together with `root=/dev/mmcblk0p67`). TWRP still booted its ramdisk (`Trying to unpack rootfs image as initramfs…` in its dmesg) because its kernel ignores the parameter. So instead of stripping it, our kernel does the same: `init/initramfs.c` accepts `skip_initramfs` and does nothing (commit `1c67115bc` on the `chef-cyclo` branch). With an initramfs providing `/init`, the bootloader's `root=`/`init=` are ignored by the kernel.

**Config fragment.** `kernel-config/chef-cyclo.config`, appended by `chef_defconfig`: `CONFIG_DEVTMPFS(+_MOUNT)=y` (Android populates `/dev` with ueventd, stock has it off), `ANDROID_PARANOID_NETWORK` off, `LOCALVERSION=-cyclo`. Kernel is now `4.4.192-cyclo-g6d83ef138-00001-g1c67115bc`.

**USB gadget.** Stock config offers configfs functions NCM (`ncm.usb0`), Qualcomm RNDIS (`rndis_bam`), FunctionFS, MTP/PTP etc. — no plain ECM/RNDIS. NCM works with the in-kernel `cdc_ncm` driver on any Linux host, so `/init` builds a single-function NCM gadget (`1d6b:0104`, locally-administered MACs), binds it to whatever appears in `/sys/class/udc` (expected `a800000.dwc3`), gives `usb0` 172.16.42.1/24, runs `udhcpd` (leases .2–.9, no router option) and `telnetd -l /bin/sh`, then `exec`s busybox init with a small inittab that respawns both. Vibrator is `/sys/class/timed_output/vibrator/enable` (ms) — used as a display-less progress signal.

**busybox.** Alpine's `busybox-static` lacks `telnetd`/`udhcpd` (they live in a dynamic `busybox-extras`); Debian's `busybox-static` 1.37 arm64 has both plus `ip`, `mdev`, `cttyhack`, so `setup-toolchain.sh` pulls that `.deb` (`dpkg-deb --fsys-tarfile`). Initramfs is ~1 MB. `mkboot.sh` uses AOSP `mkbootimg.py` with the header values read out of `stock/partitions/boot_a.img` (v0, 4096-byte pages, offsets 0x8000/0x1000000/0xf00000/0x100, os 10.0.0 / 2021-10, stock cmdline). `unpack_bootimg` on the result matches stock field for field.

### 2026-09-15 — Bluetooth survey (offline; phone awaiting battery + display)

Read from the `bluetooth_a` dump and the kernel tree, nothing tested on the device yet.

- **Chip is a WCN3990 ("Cherokee"), not ROME.** `bluetooth_a` is a 4.5 MB ext4 image holding `/image/crbtfw21.tlv` + `crnv21.bin` (v2.1 firmware + NV) alongside older `cr*11/20` and `apbtfw11`/`apnv11` sets. Android mounts it at `/vendor/bt_firmware`.
- **Transport is `/dev/ttyHS0`** (`c1af000.uart`, MSM HS UART, base_baud 460800) — already probed in our first boot. Power is `/dev/btpower` (`bluetooth-power.c`, `BT_CMD_PWR_CTRL` ioctl 0xbfad), also present; `bt_power_populate_dt_pinfo` warnings about missing `bt-reset-gpio`/`qca,bt-vdd-*` are normal for WCN3990 (it's powered through the PMIC, not GPIOs). `BTFM_SLIM_WCN3990` is on for BT audio over SLIMbus (not needed).
- **The kernel can't drive it as-is.** `CONFIG_BT_HCIUART` is off — Android does HCI entirely in userspace (`android.hardware.bluetooth@1.0-service-qti`: powers via btpower, downloads the TLV firmware over the raw UART, then speaks H4 + IBS in-band sleep). The tree's `drivers/bluetooth/hci_qca.c` only knows ROME (`qca_uart_setup_rome`); WCN3990 support landed in mainline 4.20 and depends on `serdev`, which 4.4 doesn't have.
- **Two ways to BlueZ**, both compile without the phone:
  1. Backport the WCN3990 parts of mainline `hci_qca` (`qca_wcn3990_init`, firmware/NV download via `btqca`, IBS) onto the ldisc path: userspace powers the chip through `/dev/btpower`, then `btattach -B /dev/ttyHS0 -P qca`. Cleanest end state, most kernel work.
  2. Userspace TLV loader (port of what the QTI HAL does), then `btattach -P h4` with plain `hci_uart`; IBS sleep has to be disabled or tolerated. Less kernel work, more fragile.
- Either way the first step is `CONFIG_BT_HCIUART=y` + `CONFIG_BT_HCIUART_QCA=y` (+`BT_QCA`) in `kernel-config/chef-cyclo.config`, and a rootfs bigger than the busybox initramfs to hold BlueZ.

### 2026-09-15 — Bluetooth live bring-up: BLE works

Booted a diagnostic initramfs and reproduced the WCN3990 initialization without Android. `bt-bringup` (since replaced by `bt-up`; last version in commit ae43429) powers the rails through `/dev/btpower`, sends the required UART pulses (`c0` at 2400 baud, `fc` at 115200), and issues the QCA EDL version request. The controller reports product `0x0000000a`, patch `0x0001`, ROM/build `0x0201`, and SOC `0x40020140` (Linux key `0x01400201`), confirming `crbtfw21.tlv` + `crnv21.bin`.

The probe switches both ends to 3.2 Mbaud, downloads the patch (download mode 3 suppresses all responses on this firmware), then receives success from all 19 NVM segments. For the diagnostic copy in RAM it disables IBS/deep sleep while retaining the 3.2 Mbaud setting; the stock partition is never modified. HCI Reset succeeds, and Read Local Version reports HCI/LMP 5.0, Qualcomm manufacturer `0x001d`, subversion `0x02be`.

Attaching the UART with the kernel's plain H4 line discipline creates and starts `hci0`. A 10-second raw LE scan (`btprobe lescan 0`) receives valid advertising reports from five distinct devices. This proves power, UART, stock firmware/NVM, Linux HCI, and BLE radio RX. Next integration step: package BlueZ and replace the diagnostic no-sleep NVM edit with working QCA IBS power management.

Killing the process that held the HCI line discipline exposed a dormant Motorola-tree teardown bug and caused a kernel panic/reboot: `hci_uart_tty_close` unregistered and freed the same `hci_dev` twice. The duplicated unregister/free block and a stale `rx_lock` initialization (the field no longer exists) were removed. A live regression test on the rebuilt kernel cleanly removed `hci0`, kept the phone reachable over USB networking, and produced no panic, confirming the corrected single-unregister/single-free lifetime.

The live-tested diagnostic image is `out/boot.img`, SHA-256 `347399a82148935c0f364dba312eb96603b78da6df857bbcb4c026f9dc60b066`.

### 2026-09-15 (evening) — BlueZ in the image, WCN3990 driven by the kernel, IBS sleep working

Goal: replace the diagnostic userspace loader + plain H4 with the real thing — `hci_qca` with in-band sleep — and put BlueZ on the phone.

**Rootfs.** The initramfs is now an Alpine v3.24 aarch64 root (musl, busybox + busybox-extras, dbus 1.16, BlueZ 5.86 with btmgmt/btmon/hciconfig) built on the host by the static x86_64 `apk` with `--arch aarch64 --usermode --no-scripts` (`scripts/mkrootfs.sh`, 18 MB unpacked, 6.3 MB compressed), with `initramfs/` as an overlay on top. inittab runs telnetd, udhcpd, `dbus-daemon --system`, `bluetoothd -n` (LE only, `AutoEnable`) and `bt-up`.

**Kernel** (fork branch `chef-cyclo`, all in `drivers/bluetooth` + `net/bluetooth`):
- `btqca`: backport of mainline's WCN3990 support — version request, `crbtfw%02x.tlv`/`crnv%02x.bin` names from the ROM version, download mode from the patch header (mode 3: segments sent without waiting, a command-complete injected afterwards so the HCI core's command credit and timer stay sane), `qca_set_bdaddr` (`0xFC14`, which wants the address byte-swapped — first attempt programmed `75:0D:6F:07:4B:30`), pre-shutdown command, and the unified type-4 NVM container the stock `crnv21.bin` uses (a type-2 NVM block plus a type-3 block; tags 17/27 patched inside the type-2 block). `__hci_cmd_send()` backported to hci_core for the unacked segments.
- `hci_qca`: WCN3990 setup on the ldisc path — SoC type from the DT `qca,wcn3990` node, version at 115200, switch to 3.2 Mbaud (flow control off, vendor event caught at the new rate and dropped), firmware, HCI reset, then IBS on. The IBS state machine was already there; its clock-vote stubs now call the tty's `TIOCPMGET`/`TIOCPMPUT` outside the IBS spinlock, which on msm_serial_hs is the runtime-PM reference the Android HAL used to hold. `HCI_QUIRK_INVALID_BDADDR` so the placeholder NVM address is never used.
- `hci_ldisc`: flow-control re-enable reordered (termios first, RTS last) and a combined speed+flow-control setter — see gotchas; without it the baud-change vendor event was lost in the msm_hs receiver reset and setup failed.
- `lib.c`: `%pKV` → `%pV`, which is why the Motorola kernel had never printed a readable Bluetooth log line.

**Userspace.** `bt-up` (inittab respawn): power rails on via btpower (first run) or IBS wake + pre-shutdown at 3.2 Mbaud (restart — see gotchas), `c0`/`fc` pulses, `btattach -B /dev/ttyHS0 -P qca -S 115200`, then `btprobe bdaddr 0 <androidboot.btmacaddr>` (mgmt Set Public Address, retried while the initial setup still has the adapter powered). bluetoothd powers the adapter up as soon as it is configured. `btprobe attach` takes a protocol id now, and `btprobe restart bootloader` saves a trip through Android.

**Measured on the phone** (`logs/bluez-ibs-dmesg.txt`): attach → setup complete in 0.85 s (version 6 ms, baud switch 30 ms, patch 1.02 s of which ~0.6 s is the wait for a last-segment ack that this firmware never sends — confirmed with a 3 s window — NVM 19 segments in 37 ms), address set 0.5 s later, `Powered: yes`, address `30:4B:07:6F:0D:75`. `bluetoothctl scan on` sees 9 devices (a Mi Smart Band 5 among them). Four seconds after the scan both IBS sides are asleep (`rx_ibs_state=0`, `tx_ibs_state=0`, votes off) and the UART's `power/runtime_status` reads `suspended`; over a 30 s window the UART clock was on for 7.3 s. `bluetoothctl power off`/`on` and killing `btattach` (bt-up restarts the controller from the running firmware) both recover fully.

Image: `out/boot.img`, SHA-256 `b027f7896fe587be39093650c8791f239fa5885a2657e4b95a622f153620b2d5`.

### 2026-09-15 (night) — GPS userspace: build-verified, live test pending

Two work sessions split GPS bring-up along the design in `gps-userspace-handoff.md` (§1's decision: stock Alpine `qmi-utils` talking to a home-grown QMUX bridge over `AF_MSM_IPC`, no QRTR/ModemManager/pd-mapper). **`tools/rmtfs/`** is `linux-msm/rmtfs` (BSD) with two changes: dropped `rproc.c`/the `-s` option (no `/sys/class/remoteproc` on this 4.4 kernel) and dropped `libudev` from `sharedmem.c`'s UIO/RFSA opens in favor of reading `/sys/dev/char/<major>:<minor>/...` off the already-open fd's `fstat()` — same two attributes udev would have read, no shared-lib dependency for a static musl build. `handle_rmtfs()`'s one raw `recvfrom()` on the `AF_MSM_IPC` socket is now `qrtr_recvfrom()` (a real sockaddr type doesn't exist across that boundary the way it does for QRTR, so the bridge hands back `node`/`port` and `rmtfs.c` builds a local `sockaddr_qrtr` for `qrtr_decode()`). Confirmed via code read that `storage.c` (unmodified) already gives `-r` exactly the required RAM-shadow semantics: it slurps the partition once into a malloc'd buffer read-only and never opens it again, so `gps-up`'s `rmtfs -P -r` invocation cannot write `modemst1/2`/`fsc`/the served `fsg_a`/`fsg_b` under any code path. (This session's `gps-up` did not yet pass `rmtfs -S`, on the mistaken belief that `fsg` was unsuffixed like the others; corrected 2026-09-16, see that log entry.)

**Build.** `setup-toolchain.sh` now also fetches a Bootlin `aarch64-buildroot-linux-musl` cross compiler into `toolchain/aarch64-musl/` (88 MB; needs real libc, unlike `btprobe`'s freestanding AOSP-GCC build) — the actual binary is `aarch64-buildroot-linux-musl-gcc`, not the `aarch64-linux-musl-gcc` name a first draft of this script assumed. `mkrootfs.sh` adds `qmi-utils` to `PKGS`; `apk` pulled `libqmi 1.38.0_git20260414`, `libqrtr-glib`, `libmbim`, `eudev-libs`, `glib` automatically, matching the handoff's researched versions exactly. `mkinitramfs.sh` cross-compiles `tools/rmtfs/*.c` + `tools/qrtr/{qmi,logging}.c` + `tools/msmipc.c` into `rmtfs`, and the msmipc-side files into `irsc` and `qmuxd-lite`, needing both `-I kernel/include/uapi` (for `<linux/msm_ipc.h>` itself) and `-I kernel/include` (for `<linux/compiler.h>` etc. it pulls in transitively). The helpers are now mandatory: a missing source or a failed cross-build aborts image generation rather than producing an unsafe `gps-up` without one of its dependencies.

### 2026-09-16 — GPS: active-slot `fsg` fix (build/host-verified; still no live test)

### 2026-09-16 (live, fix) — root cause found and fixed for the `EAGAIN`: a trailing newline in a sysfs write

Root-caused by reading kernel source (no phone touched) and independently re-derived by `gps-review-sonnet`: `gps-up`'s `echo /firmware/image > /sys/module/firmware_class/parameters/path` writes the string **with `echo`'s trailing `\n` included** — `kernel/params.c`'s `param_attr_store()` → `param_set_copystring()` is a bare `strcpy()` with no trimming. `drivers/base/firmware_class.c`'s `fw_get_filesystem_firmware()` then builds the direct-load path as `"%s/%s"` (search path + firmware name), so the lookup becomes `"/firmware/image\n/modem.mdt"` — a path `filp_open()` can never resolve, even though `modem.mdt` genuinely exists (confirmed offline: `debugfs -R "ls -l /image" stock/partitions/modem_a.img` shows it at 8412 bytes alongside `modem.b00`–`b28`). ### 2026-09-16 (offset fix) — RMTFS rejected every EFS sector read in that same run2 log; fixed and build-verified, not yet live-tested

Re-reading `logs/gps-fsg-live-test-2026-09-16-run2-gpsup-out.txt` in full (not just the summary above) shows `tools/rmtfs/`'s QMI handling working as designed and then failing on every single data transfer: each cycle opens `modem_fs1`/`fs2`/`fsg`/`fsc` successfully (caller ids 0–3), calls `QMI_RMTFS_ALLOC_BUFF` with `buff_size=0` and gets back `0xfd601000` (this device's RMTFS UIO region base), then issues `QMI_RMTFS_RW_IOVEC` with `phys_offset=0x200` to read sector 1 — and `[RMTFS] failed to read sector 1` every time. `grep -c "failed to read sector 1"` on that log gives exactly **115** — the same figure the entry above cites for the SMEM-crash-loop's restart count. That is unlikely to be a coincidence: this device's downstream modem firmware reports `phys_offset` as an offset *relative to* the address `rmtfs_mem_alloc()` returned, not an absolute physical address, and `tools/rmtfs/sharedmem.c`'s `rmtfs_mem_ptr()` treated it as absolute — `0x200 < rmem->address (0xfd601000)`, so every read was rejected by a bounds check, never a hardware fault. It's plausible this is what actually drove the "unrelated" crash loop above (the modem couldn't read its own EFS data and reset), but that's not confirmed here — this session did not touch the phone, so it remains a hypothesis for the next live test to check.

The same symptom, on an unrelated device (a Huawei Watch 2 LTE, MSM8909W downstream), is fixed upstream in [linux-msm/rmtfs#41](https://github.com/linux-msm/rmtfs/pull/41) ("sharedmem: accept relative buffer offsets"), open as of 2026-08-30. Its approach: auto-detect relative-vs-absolute from range (a request that fits entirely below the mapped region's size is relative; otherwise it's absolute-and-subtract, as before), with all bounds checks written as subtractions so an oversized or near-`ULONG_MAX` `phys_offset` can't wrap a `start+len` sum into a false accept the way the original code could.

**Fix, in `tools/rmtfs/sharedmem.c`**: ported the same approach as `rmtfs_mem_resolve_offset()`, replacing `rmtfs_mem_ptr()`. It takes the region's base/size instead of the opaque `struct rmtfs_mem` (so host tests can call it directly) and is shared by both `rmtfs_mem_read()`/`rmtfs_mem_write()` backends — the mmap'd-UIO path used in this live test *and* the `pread`/`pwrite` path used when `/dev/qcom_rmtfs_mem1` (rfsa) is present instead. The `pread`/`pwrite` path previously had **no bounds check at all** and, for a relative `phys_offset` like this device's, computed `phys_address - rmem->address` directly — a huge bogus offset, not merely a wrong-but-safe one; that path is fixed by the same change, even though this device currently falls back to UIO (`/dev/qcom_rmtfs_mem1` doesn't exist here — see the `failed to open` line at the top of the run2 log).

**Decision: range-based auto-detection, not a tracked alloc mode.** Considered threading a "this caller's buffer is relative" flag from `rmtfs_alloc_buf()`'s `buff_size==0` case through to `rmtfs_iovec()`, but rejected it: the QMI wire protocol carries no field saying which encoding a given `phys_offset` uses, so any such flag would be an inference on our side either way, and upstream's real-device fix already validates that inferring from range is enough. Concretely: this platform's RMTFS region sits at a multi-GB physical base (`0xfd601000`) while the mapped region itself is 2 MiB (`sdm660.dtsi`'s `qcom,rmtfs_sharedmem@0` reg is `<0x0 0x200000>`; the base observed here sits 4K past that allocation's start because of `qcom,guard-memory`), and this pairing (region size ~2000x below the base address) is guaranteed by the platform's memory map, not by anything either side of the QMI link declares — a relative offset and an absolute PA can never overlap in value here. Per-alloc mode tracking would add state with no protocol-level backing and nothing to validate it against; there is accordingly no "mode isolation between callers" test category (`rmtfs_mem_resolve_offset()` is a pure function of the values in each individual request, not of any per-caller or per-allocation state).

**`-r` (RAM-shadow) behavior is untouched** — this fix is confined to `sharedmem.c`'s address resolution; `storage.c` (which enforces `-r`) was not touched.

- **`GET_DOMAIN_LIST` (0x21)**, the message the modem's client and this kernel's own client both send: serves domain data parsed live from `/firmware/image/*.jsn` (`modemr.jsn` → `msm/modem/root_pd`/180, `modemuw.jsn` → `msm/modem/wlan_pd`/180, `adspr.jsn`/`adspua.jsn`/etc. also indexed for when ADSP is booted; the real, confirmed-0-byte `modemus.jsn` is skipped cleanly like any other malformed file). Domain name = `soc/domain/subdomain`, service key = `provider/service`, taken directly from the descriptor rather than a compiled-in table (unlike mainline's `qcom_pd_mapper.c` fallback tables for older SoCs) — see `tools/servreg-locator/jsn.c`'s file header for the exact schema. - **`INDICATION_REGISTER` (0x20)**: acked unconditionally (no live database-update stream to offer, but nothing here ever changes after startup, so that's accurate).
- **`PFR` (0x24)**, the modem's crash-report message (firmware string `SERVREG_LOC_PFR_REQ` confirmed, exact request TLV shape not independently confirmed against real hardware): best-effort decode for logging, but always acked regardless, so a wrong guess here degrades to "logged blind" rather than a hung QCCI call on the modem side.

Wire shapes are a field-for-field port of **this tree's own kernel client** (`kernel/drivers/soc/qcom/service-locator-private.h`, `service-locator.c` — the same struct layouts this kernel already sends/expects for `wlan_pd`), cross-checked against mainline's userspace-free replacement (`drivers/remoteproc/qcom_pd_mapper.c`) for the message IDs and the PFR shape the kernel-private header doesn't have. ### 2026-09-18 (qmux bridge) — the `qmicli` timeout was a one-byte CTL flag bug; reproduced and fixed on the host, image rebuilt, not yet live-tested

**Root cause, found without the phone.** The host's own `qmicli` is the same libqmi 1.38.0 as the rootfs's, and a natively built `qmuxd-lite` listens on any unix socket whose path contains `qmux_socket`, so the 2026-09-17 (live, TFTP) failure was reproduced in seconds on the host: `qmicli -d <scratch>/qmux_socket --get-service-version-info -v` timed out exactly as on the phone, and libqmi's verbose dump shows why — the bridge's CTL reply arrived (`01:16:00:80:00:00:02:01:21:00:0B:00…`) but libqmi decoded it as a CTL *indication* (`flags = "indication"`) and never matched it to transaction 1. `tools/qmux.c`'s `ctl_build_response()` set the SDU flag byte to libqrtr's `QMI_RESPONSE` (2), which is right for ordinary services (`QmiServiceFlag`: response 1<<1, indication 1<<2) but wrong for service 0 (`QmiCtlFlag`: response 1<<0, indication 1<<1). The relay path for real services was never affected — those flag bytes come from the modem untouched — so the fix is confined to the locally emulated CTL: new `QMI_CTL_FLAG_RESPONSE`/`QMI_CTL_FLAG_INDICATION` in `tools/qmux.h`, used by `ctl_build_response()`, and the `test_qmux.c` assertion that had enshrined the wrong value corrected. The handoff doc's `QMI_CTL_ERR_NOT_SUPPORTED = 0x11` was wrong the same way (libqmi prints it as `MissingArgument`; NotSupported is 0x5E) and is corrected too — cosmetic, but it was what a failed Allocate CID would have shown.

**Host-verified after the fix:** `--get-service-version-info` and `--device-open-sync` complete immediately against the host bridge (empty service list, as expected with no `AF_MSM_IPC` on the host), and a LOC client allocation fails with the honest `QMI protocol error (94): 'NotSupported'` instead of timing out. `make -C tools test`: 388/388, 43/43, 71/71, 16/16. ### 2026-09-18 (fblog) — read-only boot/probe output on the panel; build/host-verified, not live-tested

**Why.** Every fastboot-booted probe so far was blind from the phone's side: the panel showed the bootloader splash and then nothing, and only the host's telnet session knew what was running. Everything the image does already narrates itself into `/dev/kmsg` (`cyclo-init:`, `bt-up`, `gps-up:`, `fbtouch:`), so the smallest robust design is a resident viewer of that ring rather than a new logging channel: **`tools/fblog/fblog.c`**, started from inittab, tails `/dev/kmsg` (from the start of the ring, so the boot so far appears immediately) and paints it with a 9×15 bitmap font at 2× (59 columns × 68 rows on 1080×2246), newest at the bottom, long lines wrapped with a two-space indent, a header with kernel release, uptime, battery % and a `lost N` count if the ring overran it. Policy: userspace records (facility ≠ 0, i.e. anything written through `/dev/kmsg`) always; kernel records only at `KERN_ERR` or worse (`-k`, `-a` to widen). It is strictly output: no input device is opened, nothing is interactive, and it drops the mapping the moment another client wants the screen.

**Display contract, factored out.** The open → `UNBLANK` → mmap → pan → stay-resident sequence, the backlight-write-then-commit rule, the 1 Hz heartbeat commit and the `POWERDOWN`-before-last-close rule (both mdss_fb quirks live-verified on 2026-09-18) moved from `fbtouch.c` into **`tools/fbdev.h`**, which both tools now include; `fbtouch` keeps the same syscall sequence through thin wrappers (its 71 host checks unchanged). **Coexistence with `fbtouch show`** is an advisory `flock` on `/run/fb0.lock` (see the new gotcha): `fbtouch show` takes it exclusively (10 s bounded wait, explicit failure) before opening fb0 and releases it after its `POWERDOWN` + close; `fblog` holds it shared only while drawing, backs off on `EWOULDBLOCK` (unmap, keep the fd, retry every 250 ms) and resumes with `UNBLANK` + remap + redraw + backlight commit — the same panel-on/touch-resume path `fbtouch -c` already exercised live. A killed `fbtouch` releases the lock implicitly. No manual step is needed for normal `fbtouch show` use; `/run/fblog.off` + kill exists only to idle the panel deliberately (power measurements). ### 2026-09-19 (power-off, live) — PMIC hold behaviour measured from its registers; `buttond` power-long = clean power-off, verified

**Measurement, without holding anything.** The PM660's PON block keeps the power-key reset policy in twelve registers the kernel driver only *writes* when the DT gives `qcom,s2-type` (it does not here), so they can be read instead of provoked: `/sys/kernel/debug/regmap/spmi0-00/registers` is fixed-width, and `dd bs=9 skip=0x840 count=12` reads exactly those bytes and nothing else (no PMIC sweep, no clear-on-read status registers). Read first on rooted stock over `adb … su` (base64 script per the root-read rule), then again under our own kernel in the boot below — byte-identical: KPDPWR `0e 07 08 80` = S1 6720 ms, S2 2000 ms, reset type `0x8`, S2 *enabled*; RESIN `0f 07 04 00` and KPDPWR+RESIN `0f 07 04 00` = 10256 + 2000 ms, type shutdown, S2 *disabled*. `0x880` PON_TRIGGER_EN = `0xf4` (RTC, USB, PON1, CBLPWR, KPDPWR). Consequences, now in the gotchas: the only hardware reset is power held ≈8.7 s (type `0x8` is a hard-reset variant, not one of the four values the DT binding names); `msm-pm660.dtsi` wires no `kpdpwr-bark` interrupt, so software gets no warning before it; the Power+VolDown combo reset is *disabled* at the PMIC — the escape works because the 8.7 s reset reboots and VolDown held into the bootloader selects fastboot; and USB/key are power-on triggers, so a key still held when the PMIC powers down turns the phone straight back on. Every boot so far logged `Power-off reason: PS_HOLD` / `Power-on reason: Hard Reset`, i.e. the `reboot`s from our image go through the MSM's own reset path, never the PMIC timer.

**Default for unclaimed `power.long`** (`tools/buttond.c`, `-p HOLD_MS`, default 1500): at the 1.5 s `long` a 100 ms buzz and `keep holding … release now to cancel`; still held 1.5 s later (3 s in all) a 300 ms buzz and `power off ready: release the button to power off`; the **release** then logs `shutting down now`, buzzes again, `sync()`s and runs `poweroff` — busybox init's SIGUSR2 path: `::shutdown` entries, SIGTERM to every process (so `gps-up`'s cleanup runs if the modem is up), SIGKILL a second later, `reboot(RB_POWER_OFF)`; if the applet is missing the signal goes to init directly, and only if init refuses is the syscall used after a `sync`. A release before the second buzz, or a release + re-press between two ticks (the recognizer counts presses), cancels with a log line. Acting on the release rather than at a threshold is what keeps a held key from re-triggering the PMIC's KPDPWR power-on, and 3 s leaves >5 s before the hardware reset; holding past that just means the PMIC reboots the phone. A claimed `power.long` never arms this (the recorder's finish-ride will take precedence); `-p 0` keeps the old log-only behaviour. `buttond status` shows `poweroff=idle|armed|ready`. The panel is not woken for the countdown; the buzzes are the feedback. ### 2026-09-20 (audio, host only) — speaker-protection probe tooling: TX-port holder, AFE topology installer, dyndbg toggler; image rebuilt, nothing run live

**Why.** The 2026-09-20 calibrated run left FF reading `DISABLE` with "missing ACDB calibration" as the working theory. Static analysis of the stock images (facts, itemised in [Audio → Why FF stays DISABLE](features/audio.md#why-ff-stays-disable--current-evidence-2026-09-20-static-analysis-nothing-here-is-live-verified)) replaced that theory with three concrete gaps between stock and this build: (1) the TAS algorithm is a *dynamic* ADSP module (`capi_v2_smartAmp_TAS25xx.so.1` + `tas2560_TI.bin` under `/vendor/lib/rfsa/adsp`) that stock's ADSP loads through the FastRPC `apps_std` listeners `adsprpcd`/`adsprpcd audiopd`, and this image runs no FastRPC listener — the strongest (inferred) explanation; (2) the stock ACDB carries no TAS data at all, only the per-device AFE topology property `0x13150` = `0x000112FC` for the three speaker devices (mics `0x000112FB`), which stock's kernel sends as `AFE_PARAM_ID_SET_TOPOLOGY` on port `0x1004` before playback and ours never does; (3) stock starts the TERT_MI2S_TX feedback port (4101) right before FF reads 1 — the TAS module's own string says the RX side cannot open until TX is open — and neither 2026-09-19 log of this build has a single port-4101 line (an earlier note claiming a TX stream was not needed was wrong).

## Why audio needs its own subsystem bring-up

Audio on this SoC runs on the ADSP (Hexagon DSP), not the application processor. `audio-up` currently treats it as a one-shot bring-up rather than a supervised lifecycle like `gps-up`. The kernel does expose an unload command: writing `0` to `/sys/kernel/boot_adsp/boot` calls `subsystem_put()` in `kernel/drivers/soc/qcom/qdsp6v2/adsp-loader.c`. That path has not been exercised on this device, and its interaction with the registered ALSA card, APR clients and a later reload is unknown, so the shipped script deliberately leaves the ADSP running until reboot.

## Components and lifecycle

`initramfs/usr/bin/audio-up`:

1. Mounts the active slot's `modem_$SLOT` partition read-only at `/firmware` — the ADSP firmware (`adsp.mdt`/`adsp.b00`..`b21`) lives on the *modem* partition, next to the modem's own firmware, and `gps-up` already knows how to find and mount it. If `gps-up` already has `/firmware` mounted, `audio-up` reuses it and never unmounts it; if `audio-up` mounts it first, `gps-up` does the same in reverse — see both scripts' "audio-up also needs" / "gps-up may already have this mounted" comments for the exact symmetry. Neither script tears down a mount it doesn't own.
2. Sets `/sys/module/firmware_class/parameters/path` to `/firmware/image` with `printf` (no trailing newline — the same `param_set_copystring()` gotcha documented in `gps-up`'s `set_firmware_path`).
3. Runs `irsc` (idempotent) and starts a `servreg-locator` only if QMI service `0x40` isn't already served (by `gps-up` or a previous `audio-up`) — symmetric with `gps-up`'s own check. This answers the kernel audio PDR's boot-time `avs/audio` service lookup (`service_locator.enable=1` is on the bootloader cmdline); adsp-loader itself doesn't strictly need it, but stock always has a locator up by this point.
4. Sets the `adsp` `msm_subsys` device's `restart_level` to `related` (the default `system` panics the whole kernel on a subsystem crash — same reasoning as `gps-up`'s `modem` restart level).
5. Boots the ADSP: `echo 1 > /sys/kernel/boot_adsp/boot` (`CONFIG_MSM_ADSP_LOADER`, DT node `qcom,msm-adsp-loader`; the kernel side is `subsystem_get("adsp")`, which loads `adsp.mdt` via `request_firmware()` from the path set above, then sets the APR state to `LOADED`).
6. Polls `/proc/asound/cards` (up to 60 s; live it took 1.17 s) for the `sdm660-snd-card` machine driver (`kernel/sound/soc/msm/sdm660-internal.c:3142`) to register, then logs `adsp up, card 0 'sdm660sndcard' N.NNs after boot_adsp, MultiMedia1 playback pcm device 0` with the device parsed from `/proc/asound/pcm`. The check is a bare `grep` — **never `[ -s ]`**, since procfs reports size 0 for this file even when it lists the card. On timeout it dumps the last 40 kernel lines matching `adsp|asoc|snd|apr|q6|tas2560|lpass|pil`, and if it had started a locator it says so before stopping it: the ADSP stays up without a locator, but kernel PDR notifications stop.
7. If it started nothing (`gps-up` already had a locator up) it exits 0 — the ADSP needs no resident process. Otherwise (the common case on a fresh boot without GPS) it stays resident supervising the `servreg-locator` it started; `TERM` stops that locator only, the ADSP stays up.

Manual opt-in only (not in inittab), same policy as `gps-up`: run `audio-up &` from the telnet shell.

`initramfs/usr/bin/speaker-test-tone` plays a short sine tone out of the TAS2560 loudspeaker once the card is up. `tools/wavtone.c` (`wavtone`) generates the WAV file it hands to tinyalsa's `tinyplay`.

## Speaker path and mixer controls

The loudspeaker is a **TAS2560 smart amp** on I2C (`tas2560.2-004c`, DT `kernel/arch/arm64/boot/dts/qcom/sdm636-chef-audio.dtsi`), driven by the **TERT_MI2S_RX** backend (`kernel/sound/soc/msm/sdm660-internal.c:2821`, cpu dai `msm-dai-q6-mi2s.2`, codec dai `tas2560 ASI1`). The front-end is **MultiMedia1** (`msm-pcm-dsp.0`, `hw:x,0` — `sdm660-internal.c:1794`); `audio-up`/`speaker-test-tone` discover its PCM device number from `/proc/asound/pcm` rather than hardcoding it, since `msm_int_dai[]`'s ordering isn't a stable ABI. Default format is 48 kHz, S16_LE, 2 ch (`kernel/sound/soc/msm/sdm660-common.c:233`); `wavtone` matches those defaults.

The PM660L analog codec / `INT0_MI2S_RX` path is the earpiece/headphones, **not** the speaker (`qcom,wsa-disable` — there's no WSA881x on this device). Don't route audio there expecting the loudspeaker.

Mixer control names (`speaker-test-tone`, top-of-file variables, cross-checked against stock `mixer_paths.xml` and the kernel source):

| Control | Values | Source |
|---|---|---|
| `TERT_MI2S_RX Audio Mixer MultiMedia1` | 0 / 1 | DAPM mixer route, `kernel/sound/soc/msm/qdsp6v2/msm-pcm-routing-v2.c:15008` |
| `DAC Playback Volume` | 0..15 (1 dB/step) | `SOC_SINGLE_TLV`, `kernel/sound/soc/codecs/tas2560-codec.c:458` |
| `TAS2560_ALGO_CMD_SEND_CAL` | five integers: count, Rdc Q19, 0, 0, 0 | `SOC_SINGLE_MULTI_EXT`, `kernel/sound/soc/msm/tas2560-algo.c:648` |
| `TAS2560_ALGO_FF_MODULE` | `DISABLE` / `ENABLE` | `kernel/sound/soc/msm/tas2560-algo.c:429,652` |

Other TAS2560 controls exist but aren't touched: `TAS2560 Boost load`, `TAS2560 Sampling Rate`, `TAS2560 PowerCtrl`, `TAS2560 EAR Switch`, `TAS2560 PPG` (`kernel/sound/soc/codecs/tas2560-codec.c:460-467`).

### Calibrated write path verified; FF protection still disabled

`TAS2560_ALGO_FF_MODULE` is the ADSP-side speaker-protection module (`kernel/sound/soc/msm/tas2560-algo.c`, AFE ports `0x1004`/`0x1005`). Live findings (2026-09-19 run 1):

- `tinymix -D 0 set 'TAS2560_ALGO_FF_MODULE' ENABLE` (or `DISABLE`, or by index `1`) returns rc=1 `Error: invalid enum value` whenever the `TERT_MI2S_RX` AFE port is not active — the put handler forwards an AFE set-param to port `0x1004` and the DSP rejects it with no active port. So it cannot be part of the mixer setup before the stream.
- Set 1 s into a running stream the write returns rc=0 (kernel logs `Sending Rx-Enable data 1`) but an immediate get reads `Recieving Rx-Enable data 0` — the ADSP reports the module disabled regardless, presumably for want of calibration data (there is no ACDB loader on this build).

`speaker-test-tone` leaves all protection controls alone by default. With `-p`, it makes a **best-effort, never-fatal** calibrated attempt: discover the `persist` partition by `PARTNAME`, reuse it only if it is already the expected read-only mount at `/factory` (never unmounting a mount it does not own), otherwise mount it explicitly as ext4 with `-t ext4 -o ro,noload`, and read `/factory/factory/audio/tas2560_calib_rdc`. Live on 2026-09-20, persist was ext4 `/dev/mmcblk0p38`; the first prototype mounted it safely but looked for `/factory/audio/...`, so it reported the file missing and skipped protection. The corrected image mounted the same partition without any ext3/ext2 fallback diagnostics (only the expected `EXT4-fs … mounted filesystem without journal`), read the nested path, converted saved `7.081085;` to Q19 `3712528`, and unmounted `/factory` after loading it. `noload` prevents ext4 journal replay, so this probe cannot turn a read-only request into recovery writes to persist. The strict grammar and 4..16-ohm range remain host-tested; the per-device value is never embedded in the script.

After `tinyplay -M` has started, `-p` waits for `/proc/asound/cardN/pcmNp/sub0/status` to report `state: RUNNING`, applies its short settling delay, and rechecks `RUNNING` immediately before calibration. It then invokes the static `tas2560-send-cal CARD RDC_Q19` helper, which opens `/dev/snd/controlC<CARD>`, resolves the exact `TAS2560_ALGO_CMD_SEND_CAL` control, verifies integer type/count 5/range, and submits all `[1, Rdc-Q19, 0, 0, 0]` values atomically in one `SNDRV_CTL_IOCTL_ELEM_WRITE`. Only after that succeeds does the script use `tinymix` to enable and read back `TAS2560_ALGO_FF_MODULE`.

The helper is necessary because the initial live probe found Alpine tinyalsa 2.0.0 `tinymix` unsuitable for this control: it printed `Error: invalid value (1) for index 0`, emitted no `tas2560_algo_set_cal` kernel log, yet exited 0. `TAS2560_ALGO_CMD_SEND_CAL` is an INT×5 control with `get = NULL`; tinyalsa writes array elements index-at-a-time through a read-modify-write path, so it cannot read the write-only control before updating it. Parsing tinymix's output would not fix that mechanism. The helper uses only the kernel `<sound/asound.h>` UAPI and static musl, with no Android HAL, alsa-lib, or runtime tinyalsa dependency.

A missing partition/file, an unexpected or writable pre-existing mount, parse/range failure, mount/unmount failure, inactive PCM, helper failure, enable failure, or readback failure is logged but cannot fail otherwise-clean playback. Helper failure skips enable. Paths, helper command and activation polling/settling delays are environment-overridable for host tests. On the corrected live run, the helper ioctl completed and the kernel logged `tas2560_algo_set_cal [0]=1 [1]=3712528`, followed by Tx-FB, Tx-Enable, Rx-Enable, Rx-Cfg, Rdc programming and `FF set data 1`. Playback completed through mmap, the route reset to `Off`, and the mount was cleaned up. Immediate readback still returned `DISABLE` (the kernel received `0`), so the successful calibration/control sequence does not establish that protection is active.

Until device verification proves that the readback stays `ENABLE` and the DSP is actually applying calibrated protection, the amplitude ceiling remains the safety measure: `speaker-test-tone` defaults to **-20 dBFS** and clamps `-a` to **-6 dBFS**, and `wavtone` independently refuses (does not clamp) anything louder than -6 dBFS (`dbfs_to_amplitude`'s `-1` sentinel). Duration defaults to 1 s, clamped to 5 s. `DAC Playback Volume` defaults to 10; stock's initial mixer setup leaves it at 15 and the live run used 15 at -20 dBFS — `-v 15` reproduces that.

The stock images supplied the basis for this minimal path without importing the full Android audio stack. `vendor_a/etc/mixer_paths.xml` only enables `TAS2560_ALGO_FF_MODULE` in the speaker path; it does not reveal another TAS mixer-control sequence to guess. The stock 32-bit `audio.primary.sdm660.so` contains the persist path and TAS send-cal logic, while existing stock playback logs order `platform_send_audio_calibration`/the ACDB loader (AFE topology plus calibration) before `audio_extn_mot_spkr_send_cal`. `vendor_a` also contains `Speaker_cal.acdb` and `libacdbloader.so`, but the latter depends on Bionic/Android libraries and `/dev/msm_audio_cal`, so it is not directly usable in this musl initramfs.

That "missing ACDB calibration" reading was the working theory until the 2026-09-20 stock-image research below; it is superseded by the section that follows. This device's persist dump also contains F0 and Q values, but the kernel's F0/Q calibration start/stop cases say `Not Implemented`; the implemented Rdc path has already been exercised.

### Why FF stays DISABLE — current evidence (2026-09-20, static analysis; nothing here is live-verified)

Each item is marked **fact** (read directly from the stock partition images under `stock/partitions/`, the kernel tree, or the stock pstore/kernel log) or **inference**. No live run of this build has yet been made with any of it.

1. **Fact — the TAS2560 algorithm is a dynamically loaded ADSP module, not part of the AFE image.** The ADSP's AMDB table (`adsp.b18` on `modem_a`) registers `capi_v2_smartAmp_TAS25xx.so.1` as a *dynamic* CAPIv2 module (module ids `0x1000FC00` RX / `0x1000FD00` TX, preload 0). Stock ships that `.so` plus `tas2560_TI.bin` (8396-byte parameter blob; the module's own strings mention it, "Bin File Open Successful/Failed" and "smartamp TX: using ACDB parameters") in `/vendor/lib/rfsa/adsp/`. The ADSP opens such files through the FastRPC `apps_std` file service, which stock runs as two listeners, `adsprpcd` (root PD) and `adsprpcd audiopd`, both as user `media`, both opening `/dev/ion` and `/dev/adsprpc-smd-secure` (`init.target.rc`; libadsprpc's default search path is `;/vendor/lib/rfsa/adsp;/vendor/dsp`). **This initramfs runs no FastRPC listener at all.** Whether the ADSP demand-loads the module at first use or preloads it was not observable from Linux. **Inference (strong):** a module the DSP cannot load is the simplest explanation for `TAS2560_ALGO_FF_MODULE` reading back 0, and "no ACDB calibration" was the wrong diagnosis.

2. **Fact — the stock ACDB files carry nothing TAS-specific.** `vendor_a/etc/acdbdata/*.acdb` contain no TAS module or parameter ids (`0x12D13..0x12D16`), no AFE custom topology, and zero AFE-common calibration entries for the speaker devices (`Speaker_cal.acdb`'s `AFECLUT0` count is 0). The only speaker-relevant AFE item is the per-device property `0x13150` (AFE topology id, resolved by `libaudcal.so`'s `AcdbCmdGetAfeTopId`): speaker devices 14 `SPKR_PHONE_SPKR_MONO`, 15 `SPKR_PHONE_SPKR_VOICE` and 202 `SPKR_PHONE_SPKR_VOLTE_NB` → `0x000112FC`; every mic device → `0x000112FB`. `tools/acdb-afe-topology.py` (read-only, stdlib only) reproduces this from the image: `debugfs -R "dump /etc/acdbdata/Speaker_cal.acdb /tmp/Speaker_cal.acdb" stock/partitions/vendor_a.img && python3 tools/acdb-afe-topology.py /tmp/Speaker_cal.acdb`. So what stock's kernel sends before speaker playback that ours does not is one `AFE_PARAM_ID_SET_TOPOLOGY = 0x000112FC` on port `0x1004` (plus the hardware-delay parameter). Whether topology `0x112FC`'s built-in definition on the ADSP includes the TAS module cannot be settled statically (Hexagon immediates are not raw dwords); only a live run can.

3. **Fact — our kernel cannot see the DSP's answer to the FF readback.** `q6afe.c`'s `afe_callback` dispatches a `GET_PARAM` response on `payload[1] == module id` only and ignores the status word in `payload[0]`, so `Recieving Rx-Enable data 0` cannot distinguish "module disabled" from "module absent" or "DSP error". The status word is printed by `afe_callback_debug_print()` at `pr_debug`, and `SET_PARAM_V2` DSP errors are `pr_debug` in `afe_apr_send_pkt`/`afe_callback` too, so the silence of every log so far proves nothing. `CONFIG_DYNAMIC_DEBUG=y` and `CONFIG_DEBUG_FS=y` in `out/kernel/.config`, and `audio-up` already mounts debugfs, so these sites can be switched on at runtime — that is what `afe-debug` does.

4. **Fact (corrected 2026-09-20) — stock starts the TX feedback port, and our runs never did.** Stock's pstore (`stock/partitions/kpan.img`) shows, per speaker start: ~22 silent TAS set-params, `tas2560_algo_set_cal [1] = 3712527` (stock truncates the Q19 value; we round to `3712528` — harmless), Tx-FB/Tx-Enable/Rx-Enable/Rx-Cfg, the Rdc parameter returning `ADSP_EBADPARAM` *even in stock*, then FF readback = 1. A separate read-only live `dmesg` probe of the stock install (the pstore's own "4101" hits are only hex dumps) added the missing piece: ~15 ms after `Sending Rdc`, `afe_get_cal_topology_id: [AFE_TOPOLOGY_CAL] not initialized for this port 4101` — port `0x1005` (TERT_MI2S_TX) being **started** — before the readback that returns 1. The TAS module carries the string `smartamp RX: Can not open RX port until TX port is open`. Both 2026-09-19 logs of this build have zero hits for port 4101. Stock's `mixer_paths.xml` has no TERT_MI2S_TX route in the speaker path (presumably the HAL's DSM-feedback capture use case), so rather than guess a HAL route, `tert-tx-hold` uses the kernel's own `TERT MI2S_TX Hostless` front-end (`sdm660-internal.c` `hw:x,40`, cpu dai `TERT_MI2S_TX_HOSTLESS`, `msm-pcm-hostless`; DAPM route `{"TERT_MI2S_UL_HL", NULL, "TERT_MI2S_TX"}` needs no mixer switch). An earlier version of this note said a TX stream was not required; that was wrong.

5. **Fact — how a topology block can be installed and undone from userspace without ION.** `/dev/msm_audio_cal` (`audio_calibration.c`) frees **every** installed calibration block when its last file descriptor closes (`audio_cal_release` → `dealloc_all_clients`), so an installer has to stay resident while playback happens and its exit restores the pre-state. `AFE_TOPOLOGY_CAL_TYPE` needs no shared memory: one `AUDIO_SET_CALIBRATION` with `struct audio_cal_afe_top` (`cal_size 0`, `mem_handle -1`, `cal_info {topology, acdb_id, path RX_DEVICE/TX_DEVICE, sample_rate}`) is enough; with `dev_acdb_id[port] == 0` the kernel picks the first block whose path matches the port, so the acdb id is informational, and `afe_send_port_topology_id()` sends the topology at every port start. That is `afe-topology-cal`.

**What this means for the plan.** Installing the topology and expecting FF to read `ENABLE` is *not* ready to be a feature: even if `0x112FC` is the right topology and the TX port is up, the module load may still depend on a FastRPC `apps_std` listener this image does not have (options, in order of least new code: run stock's `adsprpcd` + Bionic from read-only mounts of the device's own `system_a`/`vendor_a` for an experiment only — its dependency closure is just `liblog`/`libcutils`/`libc++`/`libc`/`libm`/`libdl` + `linker64` — or a musl port of the BSD-licensed `quic/fastrpc` userspace). What is warranted now is the safe, reversible live experiment below, which will show which of the three gaps (TX port, topology, module load) actually stands between us and an `ENABLE` readback. Until FF is live-verified **and** shown to be applying protection, the -20 dBFS default, the -6 dBFS ceiling and the DAC volume maximum of 15 stay exactly as they are.

### The speaker-protection probe (`spk-protect-probe`) and its helpers

All four are in the image (`scripts/mkinitramfs.sh` fails closed if any source is missing), none is started by inittab, and none writes anything persistent. The user drives the live run from the telnet shell after `audio-up`:

```sh
spk-protect-probe                      # 4 x speaker-test-tone -p -d 3, evidence in /run/spk-protect-probe-<ts>-<pid>/
spk-protect-probe -d 2 -a -12 -v 15    # same flags/clamps as speaker-test-tone; -a/-v only passed when given
spk-protect-probe -r 112FB             # try another RX topology (hex) in phase 3
afe-debug status                       # the q6afe/tas2560 dynamic-debug sites (should all be =_ again afterwards)
```

- `afe-debug on|off|status` (`initramfs/usr/bin/afe-debug`): switches `+p`/`-p` on eleven `func` sites (`afe_callback_debug_print`, `afe_apr_send_pkt`, `afe_callback`, `__afe_port_start`, `afe_send_port_topology_id`, `afe_get_cal_topology_id`, `afe_find_cal_topo_id_by_port`, `afe_send_hw_delay`, `afe_send_cal_block`, `tas2560_algo_afe_set_param`, `tas2560_algo_afe_get_param`) through `/sys/kernel/debug/dynamic_debug/control`, mounting debugfs if needed, and **verifies each write by re-reading the listing** — the kernel accepts a `func` query that matches no site without complaint, so a renamed function would otherwise pass silently. (`q6afe_set_params_v2` is deliberately not in the list: it has no `pr_debug`; its DSP error is printed by `afe_apr_send_pkt`.)
- `afe-topology-cal [-d DEV] [-r RX_TOPO_HEX] [-a RX_ACDB_ID] [-s RATE] [-t TX_TOPO_HEX [-A TX_ACDB_ID]]` (`tools/afe-topology-cal.c`, static musl): defaults to RX topology `0x000112FC`, acdb id 14, 48000 Hz, no TX block. Opens `/dev/msm_audio_cal`, takes an exclusive `flock` (a second instance is refused rather than silently overwriting the block — the kernel matches blocks by buffer number), sends one byte-exact 48-byte `AUDIO_SET_CALIBRATION` per block (RX on buffer number 0, TX on 1 — the kernel matches topology blocks by buffer number only, so a TX block on 0 would overwrite the RX one), prints what it installed, then blocks in `sigwait`; `SIGTERM`/`SIGINT`/`SIGHUP` close the device (exit 0), which frees the block if no other fd is open. Topology 0 and out-of-range values are refused before the device is opened; an ioctl failure closes the fd and exits non-zero with the errno text; nothing but the SET ioctl is ever issued (no dealloc, no ION).
- `tert-tx-hold [-D CARD]` (`tools/tert-tx-hold.c`, static musl): finds the `TERT MI2S_TX Hostless` capture device in `/proc/asound/pcm` (never a hardcoded number; it must not match `MultiMedia1` or the plain back-end), opens `/dev/snd/pcmC<card>D<dev>c`, `HW_PARAMS` 48000 Hz / 2 ch / S16_LE / RW-interleaved / 512-frame periods × 2 (a 4096-byte buffer, inside `soc-pcm.c`'s `no_host_hardware` window and equal to the one page the hostless path allocates), `PREPARE`, `START`, prints each step's result, and holds the stream `RUNNING` (the hostless platform has no pointer callback, so nothing ever needs reading) until a signal, then `DROP` + close. Closing the PCM tears the back-end down whether or not `DROP` ran. It never touches a mixer control. Foreseeable live failure modes, from the kernel source: DPCM must find the `TERT_MI2S_TX` back-end through the switch-less route above (if the path walk does not connect it, `HW_PARAMS`/`PREPARE` succeed but no AFE port starts — the probe's summary will show no `port id: 0x1005` line); the TERT MI2S clock is shared with the RX side and reference-counted, so holding TX while the tone plays is the intended overlap. If the hostless capture refuses `HW_PARAMS` or `START` live, that is reported as such — it is not to be worked around with a MultiMedia capture.
- `spk-protect-probe [-d SECONDS] [-a AMPLITUDE_DBFS] [-v VOL] [-r TOPOLOGY_HEX]` (`initramfs/usr/bin/spk-protect-probe`): preconditions (sdm660 card present via `grep`, never `-s`; the adsp subsystem's `restart_level` must read `related` — `audio-up` sets it — so a DSP fault under a new topology cannot panic the kernel; all helpers, `dmesg` and a writable `/dev/kmsg`), then `afe-debug on` and four phases, each bracketed by `BEGIN`/`END` markers written to `/dev/kmsg` so its window can be cut out of `dmesg` afterwards: (1) **baseline** tone only; (2) **tx** `tert-tx-hold` started before the tone, `TERM`ed after it; (3) **tx-topo** `afe-topology-cal` first (the block must exist before any port starts), then `tert-tx-hold`, then the tone, helpers stopped in reverse order; (4) **restored** tone only, proving reversibility. Each phase records the kernel window, the `speaker-test-tone` log, `speaker-test-tone -s` and `/proc/asound` snapshots and the helper logs under `/run/spk-protect-probe-<ts>-<pid>/`, plus `phases.txt` (tone rc and helper states). A failing tone or a helper that refuses to start is logged and the remaining phases still run; the exit trap always kills the helpers and runs `afe-debug off`, and an interrupted run still prints the summary of what it gathered. Duration defaults to 3 s (enough for `-p`'s post-`RUNNING` sequence) with `speaker-test-tone`'s clamps (`-d` ≤ 5, `-a` ≤ -6 dBFS, `-v` ≤ 15, asserted equal by the host test); `-a`/`-v` are only passed through when given, so the -20 dBFS / volume-10 defaults are `speaker-test-tone`'s own. The one-screen summary answers, per phase: did playback complete; did port `0x1005` start (`__afe_port_start: port id: 0x1005`, `… not initialized for this port 4101`) and what did the AFE say; was `SET_TOPOLOGY` sent and acked (`AFE set topology id 0x112fc enable for port 0x1004 ret 0`, or the `get_cal_topology` failure); every `DSP returned error` line; the TAS get-param responses with their `PL#0` status word (`PL#1[0x1000fc00]`); and the FF readback from both the kernel (`Recieving Rx-Enable data N`) and `tinymix`.

Expected reading of a live result, none of which has happened yet: the baseline should reproduce the known `DISABLE`, now with a status word attached; phase 2 shows whether the hostless route brings `0x1005` up at all and whether that alone changes the readback; phase 3 adds the topology and shows whether `SET_TOPOLOGY` is acked and whether the readback or the status word changes; phase 4 must look like the baseline again. A `PL#0` that is not 0 on the get-param response, or a `DSP returned error` around the TAS set-params, would point at the missing module (item 1) rather than at either gap the helpers close.

### tinyplay must use mmap (`-M`)

Without `-M` every play on this card XRUN-loops: live, `state: XRUN`, `hw_ptr 1024, appl_ptr 0` (also with `-p 1920 -n 8` and `-p 4800 -n 4`), a 4 s tone took 7.5–8.5 s wall-clock, dmesg showed `WARNING: at .../msm-pcm-q6-v2.c:652 msm_pcm_trigger` (a `WARN_ON_ONCE` for a pending `CMD_EOS` from the XRUN-triggered stop 40 ms after start) plus ~136 `payload size of 8` lines per run, and the tone sounded broken. Cause: `msm-pcm-q6-v2`'s copy path acks each period as soon as the DSP has copied it, so ALSA's `avail` reaches `buffer_size` immediately and the core declares an XRUN (`stop_threshold` = `buffer_size`); tinyplay then prepare/rewrites in a loop. Android's HAL sidesteps this with `stop_threshold = INT_MAX` / mmap; tinyplay only exposes `-M`. With `-M`: `state: RUNNING`, `hw_ptr` trailing `appl_ptr` by 2048 frames, 4.14 s for the 4 s tone, 0 xruns, 4 `payload size` lines, tone heard properly. **Any future ALSA client on this card must use mmap or raise `stop_threshold` to the boundary.** `speaker-test-tone` always passes `-M`; period settings stay at tinyplay's default 1024×2.

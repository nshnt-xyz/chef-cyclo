## Why audio needs its own subsystem bring-up

Audio on this SoC runs on the ADSP (Hexagon DSP), not the application processor. `audio-up` currently treats it as a one-shot bring-up rather than a supervised lifecycle like `gps-up`. The kernel does expose an unload command: writing `0` to `/sys/kernel/boot_adsp/boot` calls `subsystem_put()` in `kernel/drivers/soc/qcom/qdsp6v2/adsp-loader.c`. That path has not been exercised on this device, and its interaction with the registered ALSA card, APR clients and a later reload is unknown, so the shipped script deliberately leaves the ADSP running until reboot.

## Components and lifecycle

`initramfs/usr/bin/audio-up`:

1. Mounts the active slot's `modem_$SLOT` partition read-only at `/firmware` — the ADSP firmware (`adsp.mdt`/`adsp.b00`..`b21`) lives on the *modem* partition, next to the modem's own firmware, and `gps-up` already knows how to find and mount it. If `gps-up` already has `/firmware` mounted, `audio-up` reuses it and never unmounts it; if `audio-up` mounts it first, `gps-up` does the same in reverse — see both scripts' "audio-up also needs" / "gps-up may already have this mounted" comments for the exact symmetry. Neither script tears down a mount it doesn't own.
2. Sets `/sys/module/firmware_class/parameters/path` to `/firmware/image` with `printf` (no trailing newline — the same `param_set_copystring()` gotcha documented in `gps-up`'s `set_firmware_path`).
3. Runs `irsc` (idempotent) and starts a `servreg-locator` only if QMI service `0x40` isn't already served (by `gps-up` or a previous `audio-up`) — symmetric with `gps-up`'s own check. This answers the kernel audio PDR's boot-time `avs/audio` service lookup (`service_locator.enable=1` is on the bootloader cmdline); adsp-loader itself doesn't strictly need it, but stock always has a locator up by this point.
4. Sets the `adsp` `msm_subsys` device's `restart_level` to `related` (the default `system` panics the whole kernel on a subsystem crash — same reasoning as `gps-up`'s `modem` restart level).
5. Boots the ADSP: `echo 1 > /sys/kernel/boot_adsp/boot` (`CONFIG_MSM_ADSP_LOADER`, DT node `qcom,msm-adsp-loader`; the kernel side is `subsystem_get("adsp")`, which loads `adsp.mdt` via `request_firmware()` from the path set above, then sets the APR state to `LOADED`).
6. Polls `/proc/asound/cards` (up to 60 s; live it took 1.17 s) for the `sdm660-snd-card` machine driver (`kernel/sound/soc/msm/sdm660-internal.c:3142`) to register, then logs `adsp up, card 0 'sdm660sndcard' N.NNs after boot_adsp, MultiMedia1 playback pcm device 0` with the device parsed from `/proc/asound/pcm`. The check is a bare `grep` — **never `[ -s ]`**, since procfs reports size 0 for this file even when it lists the card. On timeout it dumps the last 40 kernel lines matching `adsp|asoc|snd|apr|q6|tas2560|lpass|pil`, and if it had started a locator it says so before stopping it: the ADSP stays up without a locator, but kernel PDR notifications stop.
7. If it started nothing (`gps-up` already had a locator up) it exits 0 — the ADSP needs no resident process. Otherwise (the common case on a fresh boot without GPS) it stays resident supervising the `servreg-locator` it started; `TERM` stops that locator only, the ADSP stays up.

Manual opt-in only (not in inittab), same policy as `gps-up`: run `audio-up &` from the telnet shell.

`initramfs/usr/bin/speaker-test-tone` plays a short sine tone out of the TAS2560 loudspeaker once the card is up. `tools/wavtone.c` (`wavtone`) generates the WAV file it hands to tinyalsa's `tinyplay`.

## Speaker path and mixer controls

The loudspeaker is a **TAS2560 smart amp** on I2C (`tas2560.2-004c`, DT `kernel/arch/arm64/boot/dts/qcom/sdm636-chef-audio.dtsi`), driven by the **TERT_MI2S_RX** backend (`kernel/sound/soc/msm/sdm660-internal.c:2821`, cpu dai `msm-dai-q6-mi2s.2`, codec dai `tas2560 ASI1`). The front-end is **MultiMedia1** (`msm-pcm-dsp.0`, `hw:x,0` — `sdm660-internal.c:1794`); `audio-up`/`speaker-test-tone` discover its PCM device number from `/proc/asound/pcm` rather than hardcoding it, since `msm_int_dai[]`'s ordering isn't a stable ABI. Default format is 48 kHz, S16_LE, 2 ch (`kernel/sound/soc/msm/sdm660-common.c:233`); `wavtone` matches those defaults.

The PM660L analog codec / `INT0_MI2S_RX` path is the earpiece/headphones, **not** the speaker (`qcom,wsa-disable` — there's no WSA881x on this device). Don't route audio there expecting the loudspeaker.

Mixer control names (`speaker-test-tone`, top-of-file variables, cross-checked against stock `mixer_paths.xml` and the kernel source):

| Control | Values | Source |
|---|---|---|
| `TERT_MI2S_RX Audio Mixer MultiMedia1` | 0 / 1 | DAPM mixer route, `kernel/sound/soc/msm/qdsp6v2/msm-pcm-routing-v2.c:15008` |
| `DAC Playback Volume` | 0..15 (1 dB/step) | `SOC_SINGLE_TLV`, `kernel/sound/soc/codecs/tas2560-codec.c:458` |
| `TAS2560_ALGO_CMD_SEND_CAL` | five integers: count, Rdc Q19, 0, 0, 0 | `SOC_SINGLE_MULTI_EXT`, `kernel/sound/soc/msm/tas2560-algo.c:648` |
| `TAS2560_ALGO_FF_MODULE` | `DISABLE` / `ENABLE` | `kernel/sound/soc/msm/tas2560-algo.c:429,652` |

Other TAS2560 controls exist but aren't touched: `TAS2560 Boost load`, `TAS2560 Sampling Rate`, `TAS2560 PowerCtrl`, `TAS2560 EAR Switch`, `TAS2560 PPG` (`kernel/sound/soc/codecs/tas2560-codec.c:460-467`).

### Calibrated write path verified; FF protection still disabled

`TAS2560_ALGO_FF_MODULE` is the ADSP-side speaker-protection module (`kernel/sound/soc/msm/tas2560-algo.c`, AFE ports `0x1004`/`0x1005`). Live findings (2026-09-19 run 1):

- `tinymix -D 0 set 'TAS2560_ALGO_FF_MODULE' ENABLE` (or `DISABLE`, or by index `1`) returns rc=1 `Error: invalid enum value` whenever the `TERT_MI2S_RX` AFE port is not active — the put handler forwards an AFE set-param to port `0x1004` and the DSP rejects it with no active port. So it cannot be part of the mixer setup before the stream.
- Set 1 s into a running stream the write returns rc=0 (kernel logs `Sending Rx-Enable data 1`) but an immediate get reads `Recieving Rx-Enable data 0` — the ADSP reports the module disabled regardless, presumably for want of calibration data (there is no ACDB loader on this build).

`speaker-test-tone` leaves all protection controls alone by default. With `-p`, it makes a **best-effort, never-fatal** calibrated attempt: discover the `persist` partition by `PARTNAME`, reuse it only if it is already the expected read-only mount at `/factory` (never unmounting a mount it does not own), otherwise mount it explicitly as ext4 with `-t ext4 -o ro,noload`, and read `/factory/factory/audio/tas2560_calib_rdc`. Live on 2026-09-20, persist was ext4 `/dev/mmcblk0p38`; the first prototype mounted it safely but looked for `/factory/audio/...`, so it reported the file missing and skipped protection. The corrected image mounted the same partition without any ext3/ext2 fallback diagnostics (only the expected `EXT4-fs … mounted filesystem without journal`), read the nested path, converted saved `7.081085;` to Q19 `3712528`, and unmounted `/factory` after loading it. `noload` prevents ext4 journal replay, so this probe cannot turn a read-only request into recovery writes to persist. The strict grammar and 4..16-ohm range remain host-tested; the per-device value is never embedded in the script.

After `tinyplay -M` has started, `-p` waits for `/proc/asound/cardN/pcmNp/sub0/status` to report `state: RUNNING`, applies its short settling delay, and rechecks `RUNNING` immediately before calibration. It then invokes the static `tas2560-send-cal CARD RDC_Q19` helper, which opens `/dev/snd/controlC<CARD>`, resolves the exact `TAS2560_ALGO_CMD_SEND_CAL` control, verifies integer type/count 5/range, and submits all `[1, Rdc-Q19, 0, 0, 0]` values atomically in one `SNDRV_CTL_IOCTL_ELEM_WRITE`. Only after that succeeds does the script use `tinymix` to enable and read back `TAS2560_ALGO_FF_MODULE`.

The helper is necessary because the initial live probe found Alpine tinyalsa 2.0.0 `tinymix` unsuitable for this control: it printed `Error: invalid value (1) for index 0`, emitted no `tas2560_algo_set_cal` kernel log, yet exited 0. `TAS2560_ALGO_CMD_SEND_CAL` is an INT×5 control with `get = NULL`; tinyalsa writes array elements index-at-a-time through a read-modify-write path, so it cannot read the write-only control before updating it. Parsing tinymix's output would not fix that mechanism. The helper uses only the kernel `<sound/asound.h>` UAPI and static musl, with no Android HAL, alsa-lib, or runtime tinyalsa dependency.

A missing partition/file, an unexpected or writable pre-existing mount, parse/range failure, mount/unmount failure, inactive PCM, helper failure, enable failure, or readback failure is logged but cannot fail otherwise-clean playback. Helper failure skips enable. Paths, helper command and activation polling/settling delays are environment-overridable for host tests. On the corrected live run, the helper ioctl completed and the kernel logged `tas2560_algo_set_cal [0]=1 [1]=3712528`, followed by Tx-FB, Tx-Enable, Rx-Enable, Rx-Cfg, Rdc programming and `FF set data 1`. Playback completed through mmap, the route reset to `Off`, and the mount was cleaned up. Immediate readback still returned `DISABLE` (the kernel received `0`), so the successful calibration/control sequence does not establish that protection is active.

Until device verification proves that the readback stays `ENABLE` and the DSP is actually applying calibrated protection, the amplitude ceiling remains the safety measure: `speaker-test-tone` defaults to **-20 dBFS** and clamps `-a` to **-6 dBFS**, and `wavtone` independently refuses (does not clamp) anything louder than -6 dBFS (`dbfs_to_amplitude`'s `-1` sentinel). Duration defaults to 1 s, clamped to 5 s. `DAC Playback Volume` defaults to 10; stock's initial mixer setup leaves it at 15 and the live run used 15 at -20 dBFS — `-v 15` reproduces that.

The stock images supplied the basis for this minimal path without importing the full Android audio stack. `vendor_a/etc/mixer_paths.xml` only enables `TAS2560_ALGO_FF_MODULE` in the speaker path; it does not reveal another TAS mixer-control sequence to guess. The stock 32-bit `audio.primary.sdm660.so` contains the persist path and TAS send-cal logic, while existing stock playback logs order `platform_send_audio_calibration`/the ACDB loader (AFE topology plus calibration) before `audio_extn_mot_spkr_send_cal`. `vendor_a` also contains `Speaker_cal.acdb` and `libacdbloader.so`, but the latter depends on Bionic/Android libraries and `/dev/msm_audio_cal`, so it is not directly usable in this musl initramfs.

That "missing ACDB calibration" reading was the working theory until the 2026-09-20 stock-image research below; it is superseded by the section that follows. This device's persist dump also contains F0 and Q values, but the kernel's F0/Q calibration start/stop cases say `Not Implemented`; the implemented Rdc path has already been exercised.

### Why FF stays DISABLE — current evidence (2026-09-20, static analysis; nothing here is live-verified)

Each item is marked **fact** (read directly from the stock partition images under `stock/partitions/`, the kernel tree, or the stock pstore/kernel log) or **inference**. No live run of this build has yet been made with any of it.

1. **Fact — the TAS2560 algorithm is a dynamically loaded ADSP module, not part of the AFE image.** The ADSP's AMDB table (`adsp.b18` on `modem_a`) registers `capi_v2_smartAmp_TAS25xx.so.1` as a *dynamic* CAPIv2 module (module ids `0x1000FC00` RX / `0x1000FD00` TX, preload 0). Stock ships that `.so` plus `tas2560_TI.bin` (8396-byte parameter blob; the module's own strings mention it, "Bin File Open Successful/Failed" and "smartamp TX: using ACDB parameters") in `/vendor/lib/rfsa/adsp/`. The ADSP opens such files through the FastRPC `apps_std` file service, which stock runs as two listeners, `adsprpcd` (root PD) and `adsprpcd audiopd`, both as user `media`, both opening `/dev/ion` and `/dev/adsprpc-smd-secure` (`init.target.rc`; libadsprpc's default search path is `;/vendor/lib/rfsa/adsp;/vendor/dsp`). **This initramfs runs no FastRPC listener at all.** Whether the ADSP demand-loads the module at first use or preloads it was not observable from Linux. **Inference (strong):** a module the DSP cannot load is the simplest explanation for `TAS2560_ALGO_FF_MODULE` reading back 0, and "no ACDB calibration" was the wrong diagnosis.

2. **Fact — the stock ACDB files carry nothing TAS-specific.** `vendor_a/etc/acdbdata/*.acdb` contain no TAS module or parameter ids (`0x12D13..0x12D16`), no AFE custom topology, and zero AFE-common calibration entries for the speaker devices (`Speaker_cal.acdb`'s `AFECLUT0` count is 0). The only speaker-relevant AFE item is the per-device property `0x13150` (AFE topology id, resolved by `libaudcal.so`'s `AcdbCmdGetAfeTopId`): speaker devices 14 `SPKR_PHONE_SPKR_MONO`, 15 `SPKR_PHONE_SPKR_VOICE` and 202 `SPKR_PHONE_SPKR_VOLTE_NB` → `0x000112FC`; every mic device → `0x000112FB`. `tools/acdb-afe-topology.py` (read-only, stdlib only) reproduces this from the image: `debugfs -R "dump /etc/acdbdata/Speaker_cal.acdb /tmp/Speaker_cal.acdb" stock/partitions/vendor_a.img && python3 tools/acdb-afe-topology.py /tmp/Speaker_cal.acdb`. So what stock's kernel sends before speaker playback that ours does not is one `AFE_PARAM_ID_SET_TOPOLOGY = 0x000112FC` on port `0x1004` (plus the hardware-delay parameter). Whether topology `0x112FC`'s built-in definition on the ADSP includes the TAS module cannot be settled statically (Hexagon immediates are not raw dwords); only a live run can.

3. **Fact — our kernel cannot see the DSP's answer to the FF readback.** `q6afe.c`'s `afe_callback` dispatches a `GET_PARAM` response on `payload[1] == module id` only and ignores the status word in `payload[0]`, so `Recieving Rx-Enable data 0` cannot distinguish "module disabled" from "module absent" or "DSP error". The status word is printed by `afe_callback_debug_print()` at `pr_debug`, and `SET_PARAM_V2` DSP errors are `pr_debug` in `afe_apr_send_pkt`/`afe_callback` too, so the silence of every log so far proves nothing. `CONFIG_DYNAMIC_DEBUG=y` and `CONFIG_DEBUG_FS=y` in `out/kernel/.config`, and `audio-up` already mounts debugfs, so these sites can be switched on at runtime — that is what `afe-debug` does.

4. **Fact (corrected 2026-09-20) — stock starts the TX feedback port, and our runs never did.** Stock's pstore (`stock/partitions/kpan.img`) shows, per speaker start: ~22 silent TAS set-params, `tas2560_algo_set_cal [1] = 3712527` (stock truncates the Q19 value; we round to `3712528` — harmless), Tx-FB/Tx-Enable/Rx-Enable/Rx-Cfg, the Rdc parameter returning `ADSP_EBADPARAM` *even in stock*, then FF readback = 1. A separate read-only live `dmesg` probe of the stock install (the pstore's own "4101" hits are only hex dumps) added the missing piece: ~15 ms after `Sending Rdc`, `afe_get_cal_topology_id: [AFE_TOPOLOGY_CAL] not initialized for this port 4101` — port `0x1005` (TERT_MI2S_TX) being **started** — before the readback that returns 1. The TAS module carries the string `smartamp RX: Can not open RX port until TX port is open`. Both 2026-09-19 logs of this build have zero hits for port 4101. Stock's `mixer_paths.xml` has no TERT_MI2S_TX route in the speaker path (presumably the HAL's DSM-feedback capture use case), so rather than guess a HAL route, `tert-tx-hold` uses the kernel's own `TERT MI2S_TX Hostless` front-end (`sdm660-internal.c` `hw:x,40`, cpu dai `TERT_MI2S_TX_HOSTLESS`, `msm-pcm-hostless`; DAPM route `{"TERT_MI2S_UL_HL", NULL, "TERT_MI2S_TX"}` needs no mixer switch). An earlier version of this note said a TX stream was not required; that was wrong.

5. **Fact (corrected 2026-09-22 by the live run) — how a topology block is installed from userspace without ION, and why it cannot be taken back.** `AFE_TOPOLOGY_CAL_TYPE` needs no shared memory: one `AUDIO_SET_CALIBRATION` with `struct audio_cal_afe_top` (`cal_size 0`, `mem_handle -1`, `cal_info {topology, acdb_id, path RX_DEVICE/TX_DEVICE, sample_rate}`) is enough — `cal_utils_set_cal()` takes the `mem_handle <= 0` branch and calls `create_cal_block()` rather than requiring an allocation. Blocks of this cal type are matched by **buffer number alone** (`cal_utils_match_buf_num`), which is why the RX block is buffer 0 and a TX block must be buffer 1. At port start, `afe_find_cal_topo_id_by_port()` walks the list and compares `afe_top->path` against the port's direction; it then checks `this_afe.dev_acdb_id[afe_port_index]`, and **only when that is 0 does it return the first path-matching block regardless of acdb id** — if the kernel has a non-zero `dev_acdb_id` for the port (set from `this_afe.rt_cb`, the ACDB routing callback an ACDB loader would install), the block's `acdb_id` must match it exactly or the block is skipped. On this build there is no ACDB loader and no `rt_cb`, so `dev_acdb_id` stays 0 and our acdb id is informational — but that is a property of *this* configuration, not of the kernel. `afe_send_port_topology_id()` then sends the topology at every port start. That is `afe-topology-cal`. **This item previously claimed that closing `/dev/msm_audio_cal` frees every installed block and that an installer's exit restores the pre-state. That was wrong** — see [the live run](#the-topology-cannot-be-undone-by-closing-the-device). `audio_cal_release()` does call `dealloc_all_clients()`, but `call_deallocs()` begins `if (client_info_node->callbacks->dealloc == NULL) continue;`, and `q6afe.c` registers `AFE_TOPOLOGY_CAL_TYPE` with a NULL `dealloc`. So closing the device frees **no** block of this type, `AUDIO_DEALLOCATE_CALIBRATION` is a no-op for it, and the installer's residency buys only the `flock`. (Other cal types that *do* register a `dealloc` — `AFE_CUST_TOPOLOGY_CAL_TYPE` registers `afe_dealloc_cal` — are freed on last close, which is where the original over-general claim came from.) Installing is a one-way door for the boot: `afe-topology-cal -N` can neutralise the block (topology 0) so nothing is sent, but the block itself is permanent and a reboot is the only verified reset.

**What this means for the plan.** Installing the topology and expecting FF to read `ENABLE` is *not* ready to be a feature: even if `0x112FC` is the right topology and the TX port is up, the module load may still depend on a FastRPC `apps_std` listener this image does not have (options, in order of least new code: run stock's `adsprpcd` + Bionic from read-only mounts of the device's own `system_a`/`vendor_a` for an experiment only — its dependency closure is just `liblog`/`libcutils`/`libc++`/`libc`/`libm`/`libdl` + `linker64` — or a musl port of the BSD-licensed `quic/fastrpc` userspace). What is warranted now is the safe, reversible live experiment below, which will show which of the three gaps (TX port, topology, module load) actually stands between us and an `ENABLE` readback. Until FF is live-verified **and** shown to be applying protection, the -20 dBFS default, the -6 dBFS ceiling and the DAC volume maximum of 15 stay exactly as they are.

### The speaker-protection probe (`spk-protect-probe`) and its helpers

All four are in the image (`scripts/mkinitramfs.sh` fails closed if any source is missing), none is started by inittab, and none writes anything persistent. The user drives the live run from the telnet shell after `audio-up`:

```sh
spk-protect-probe                      # 4 x speaker-test-tone -p -d 3, evidence in /run/spk-protect-probe-<ts>-<pid>/
spk-protect-probe -d 2 -a -12 -v 15    # same flags/clamps as speaker-test-tone; -a/-v only passed when given
spk-protect-probe -r 112FB             # try another RX topology (hex) in phase 3
afe-debug status                       # the q6afe/tas2560 dynamic-debug sites (should all be =_ again afterwards)
```

- `afe-debug on|off|status` (`initramfs/usr/bin/afe-debug`): switches `+p`/`-p` on eleven `func` sites (`afe_callback_debug_print`, `afe_apr_send_pkt`, `afe_callback`, `__afe_port_start`, `afe_send_port_topology_id`, `afe_get_cal_topology_id`, `afe_find_cal_topo_id_by_port`, `afe_send_hw_delay`, `afe_send_cal_block`, `tas2560_algo_afe_set_param`, `tas2560_algo_afe_get_param`) through `/sys/kernel/debug/dynamic_debug/control`, mounting debugfs if needed, and **verifies each write by re-reading the listing** — the kernel accepts a `func` query that matches no site without complaint, so a renamed function would otherwise pass silently. (`q6afe_set_params_v2` is deliberately not in the list: it has no `pr_debug`; its DSP error is printed by `afe_apr_send_pkt`.)
- `afe-topology-cal [-d DEV] [-r RX_TOPO_HEX] [-a RX_ACDB_ID] [-s RATE] [-t TX_TOPO_HEX [-A TX_ACDB_ID]]` (`tools/afe-topology-cal.c`, static musl): defaults to RX topology `0x000112FC`, acdb id 14, 48000 Hz, no TX block. Opens `/dev/msm_audio_cal`, takes an exclusive `flock` (a second instance is refused rather than silently overwriting the block — the kernel matches blocks by buffer number), sends one byte-exact 48-byte `AUDIO_SET_CALIBRATION` per block (RX on buffer number 0, TX on 1 — the kernel matches topology blocks by buffer number only, so a TX block on 0 would overwrite the RX one), prints what it installed, then blocks in `sigwait`; `SIGTERM`/`SIGINT`/`SIGHUP` close the device and exit 0. **Exiting does not remove the block** — the residency now buys only the `flock` and a lifecycle for the driving script to scope the experiment with. `-N` is the one-shot neutralise: it rewrites buffer 0 (RX) with topology 0 and exits immediately without waiting for a signal, since there is nothing to hold up; it refuses `-r` and `-t`, and an install may still never carry topology 0. Topology 0 and out-of-range values are refused before the device is opened; an ioctl failure closes the fd and exits non-zero with the errno text; nothing but the SET ioctl is ever issued (no dealloc, no ION).
- `tert-tx-hold [-D CARD]` (`tools/tert-tx-hold.c`, static musl): finds the `TERT MI2S_TX Hostless` capture device in `/proc/asound/pcm` (never a hardcoded number; it must not match `MultiMedia1` or the plain back-end), opens `/dev/snd/pcmC<card>D<dev>c`, `HW_PARAMS` 48000 Hz / 2 ch / S16_LE / RW-interleaved / 512-frame periods × 2 (a 4096-byte buffer, inside `soc-pcm.c`'s `no_host_hardware` window and equal to the one page the hostless path allocates), `PREPARE`, `START`, prints each step's result, and holds the stream `RUNNING` (the hostless platform has no pointer callback, so nothing ever needs reading) until a signal, then `DROP` + close. Closing the PCM tears the back-end down whether or not `DROP` ran. It never touches a mixer control. Foreseeable live failure modes, from the kernel source: DPCM must find the `TERT_MI2S_TX` back-end through the switch-less route above (if the path walk does not connect it, `HW_PARAMS`/`PREPARE` succeed but no AFE port starts — the probe's summary will show no `port id: 0x1005` line); the TERT MI2S clock is shared with the RX side and reference-counted, so holding TX while the tone plays is the intended overlap. If the hostless capture refuses `HW_PARAMS` or `START` live, that is reported as such — it is not to be worked around with a MultiMedia capture. Three further facts were read out of the kernel tree on 2026-09-22 (static, nothing live): (a) `soc_pcm_open` jumps straight to `dynamic:` for a `no_pcm` back-end, so the codec/cpu format-compatibility check is skipped and `tas2560 ASI1` declaring **playback only** (`tas2560-codec.c:225`) does not by itself stop the `TERT_MI2S_TX` back-end opening; (b) the MI2S bit clock is derived per direction in `update_mi2s_clk_val()` as `sample_rate × 2 × bits`, and `mi2s_rx_cfg[TERT_MI2S]` and `mi2s_tx_cfg[TERT_MI2S]` both default to 48 kHz/S16_LE → **1.536 MHz either way**, so the reference-counted overlap (TX opens the interface first, the tone's RX start finds `ref_cnt` already 1 and does not re-set the clock) cannot change the clock the tone plays at — that holds only while the `TERT_MI2S_TX SampleRate`/`Format` controls are left at their defaults; (c) `mi2s_tx_cfg[TERT_MI2S].channels` is **1**, and `msm_common_be_hw_params_fixup()` pins the back-end to it, so port `0x1005` will start **mono** no matter that the front-end asks for two channels. Stock's DSM feedback is a voltage/current pair, so a mono feedback port is a plausible reason for the module to stay unhappy even once `0x1005` is up; `TERT_MI2S_TX Channels` (`sdm660-common.c:1967`) is the control that would change it. That is a question for the live summary to answer, not something to change blind — the probe deliberately touches no mixer control.
- `spk-protect-probe [-d SECONDS] [-a AMPLITUDE_DBFS] [-v VOL] [-r TOPOLOGY_HEX]` (`initramfs/usr/bin/spk-protect-probe`): preconditions (sdm660 card present via `grep`, never `-s`; the adsp subsystem's `restart_level` must read `RELATED` — `audio-up` sets it — so a DSP fault under a new topology cannot panic the kernel; the comparison is case- and whitespace-insensitive because the kernel's show side is uppercase while its store side is `strncasecmp` (this exact mismatch blocked the 2026-09-22 live attempt), and the verbatim readback is what gets logged and written to `restart_level.txt`; all helpers, `dmesg` and a writable `/dev/kmsg`), then it derives the card number from the sdm660 line of `/proc/asound/cards` (never assumed to be 0; it is exported so `speaker-test-tone` and `tert-tx-hold -D` work on the same card), runs `afe-debug on` and four phases, each bracketed by `BEGIN`/`END` markers written to `/dev/kmsg` so its window can be cut out of `dmesg` afterwards. **Both markers carry this invocation's run id** (`spk-protect-probe[<ts>-<pid>] BEGIN <phase>`, the same id the evidence directory is named after), so a second probe run in the same boot writes its own windows and no window can ever splice one run's `BEGIN` to another's `END`. Each window is checked for both markers and recorded as `window=ok`, `window=truncated` (`BEGIN` found, `END` not: the ring buffer wrapped or `dmesg` was cut mid-phase) or `window=missing` (no `BEGIN` at all); anything but `ok` is logged as it happens and heads that phase in the summary with a `WARNING` saying the kernel sections below are incomplete and their emptiness is **not** evidence that the line never appeared. The phases are: (1) **baseline** tone only; (2) **tx** `tert-tx-hold` started before the tone, `TERM`ed after it; (3) **tx-topo** `afe-topology-cal` first (the block must exist before any port starts), then `tert-tx-hold`, then the tone, helpers stopped in reverse order; (4) **neutralised** — `afe-topology-cal -N` (a one-shot that writes topology 0 and exits), then a tone with no helpers. Phase 4 is *not* called "restored" and does not rely on closing the device, because closing frees nothing (see above); its kernel window has to show `topology id 0x0 … ret -22` and no `0x112fc … ret 0`. The order is fixed: everything measured on an untouched device happens before phase 3, and a second run in the same boot is refused (sentinel `<RUN_DIR>/spk-protect-probe.topology-installed` on tmpfs) unless `-F` is given, which then labels every phase as not-a-baseline. Each phase records the kernel window, the `speaker-test-tone` log, `speaker-test-tone -s` and `/proc/asound` snapshots and the helper logs under `/run/spk-protect-probe-<ts>-<pid>/`, plus `phases.txt` (tone rc and helper states). A failing tone or a helper that refuses to start is logged and the remaining phases still run; the exit trap always kills the helpers and runs `afe-debug off`, and an interrupted run still prints the summary of what it gathered. Duration defaults to 3 s (enough for `-p`'s post-`RUNNING` sequence) with `speaker-test-tone`'s clamps (`-d` ≤ 5, `-a` ≤ -6 dBFS, `-v` ≤ 15, asserted equal by the host test); `-a`/`-v` are only passed through when given, so the -20 dBFS / volume-10 defaults are `speaker-test-tone`'s own. The one-screen summary answers, per phase: did playback complete; did port `0x1005` start (`__afe_port_start: port id: 0x1005`, `… not initialized for this port 4101`) and what did the AFE say; was `SET_TOPOLOGY` sent and acked (`AFE set topology id 0x112fc enable for port 0x1004 ret 0`, or the `get_cal_topology` failure); every `DSP returned error` line; the TAS get-param responses with their `PL#0` status word (`PL#1[0x1000fc00]`); and the FF readback under two separate, labelled headings — `FF readback (kernel log, q6afe/tas2560):` for what the DSP told the kernel (`Recieving Rx-Enable data N`, `FF set data N`) and `FF readback + protection log (speaker-test-tone/tinymix):` for what userspace then read back. They are different evidence (the kernel's `afe_callback` ignores the `GET_PARAM` status word) and are never merged into one list.

Expected reading of a live result, none of which has happened yet: the baseline should reproduce the known `DISABLE`, now with a status word attached; phase 2 shows whether the hostless route brings `0x1005` up at all and whether that alone changes the readback; phase 3 adds the topology and shows whether `SET_TOPOLOGY` is acked and whether the readback or the status word changes; phase 4 must look like the baseline again. A `PL#0` that is not 0 on the get-param response, or a `DSP returned error` around the TAS set-params, would point at the missing module (item 1) rather than at either gap the helpers close.

### Live attempt 2026-09-22: blocked at the `restart_level` precondition

Image `6084de39…` / initramfs `92daeda3…`, `fastboot boot`, user at the phone. `audio-up` worked exactly as before — `modem_a` mounted read-only, the locator published service `0x40` with 9 descriptors, and `adsp up, card 0 'sdm660sndcard' 1.59s after boot_adsp, MultiMedia1 playback pcm device 0`. `spk-protect-probe` then refused with rc=1:

```
spk-protect-probe: adsp restart_level is 'RELATED', not 'related' (audio-up sets it); refusing …
```

**No tone played, no helper started, `afe-debug` was never switched on, and nothing was written to persist or flashed.** The phone is back on stock. Evidence: `logs/audio-spk-protect-blocked-20260922T165036Z-{notes,dmesg-full}.txt`.

The defect is real and was ours. The kernel's two `restart_level` sides disagree in case: `restart_level_store()` matches with `strncasecmp`, so `audio-up`'s `echo related` is accepted, but `restart_level_show()` prints `restart_levels[]` verbatim and that table is **uppercase** — `{[RESET_SOC] = "SYSTEM", [RESET_SUBSYS_COUPLED] = "RELATED"}`, `kernel/drivers/soc/qcom/subsystem_restart.c:92`. The probe compared the readback against the lowercase spelling it had written, and the host fixture had the same lowercase spelling, so the suite could never catch it. The comparison is now case- and whitespace-insensitive (`normalize_level`), the verbatim readback is still what gets logged and stored in `restart_level.txt`, and the fixtures use the kernel's own `RELATED`/`SYSTEM` so the pre-fix code fails the suite. `audio-up` and `gps-up` only ever *write* `related` and never read it back, so neither was affected.

The run did confirm, for the first time on the device, the two things `tert-tx-hold` depends on discovering:

- **`00-40: TERT MI2S_TX Hostless (*) :  : capture 1`** is present in `/proc/asound/pcm` — the hostless capture front-end this build's `CONFIG_SND_SOC_TAS2560=y` machine driver registers really does exist at `hw:0,40`, in exactly the line shape `tert_tx_parse_pcm_line()` matches (card 0, device 40, a `capture` line whose name contains `TERT MI2S_TX Hostless`). The host fixture's shape was right. Note the adjacent `00-37: Tertiary MI2S_RX Hostless` and `00-11: INT3 MI2S_TX Hostless`, both of which the matcher must *not* take — the host test covers both.
- The card is `0` and `MultiMedia1` is device `0`, with `TERT_MI2S_RX Audio Mixer MultiMedia1: Off`, `DAC Playback Volume: 15`, `TAS2560_ALGO_FF_MODULE: > DISABLE, ENABLE` at rest — unchanged from the 2026-09-19 runs. The probe no longer assumes card 0 regardless (it derives it), but nothing yet contradicts the assumption.

`restart_level` for the four subsystems read `venus: SYSTEM`, `a512_zap: SYSTEM`, `adsp: RELATED`, `modem: SYSTEM` — i.e. `audio-up` had done its job and the guard was protecting a condition that was already satisfied.

Evidence: `logs/audio-spk-protect-live-20260922T173535Z-{notes,dmesg-full,evidence.tgz}`. What it establishes:

1. **The `DISABLE` readback was an error reply all along.** Every TAS get-param response was `code = 0x10106 PL#0[0x2], PL#1[0x1000fc00]`, and `0x2` is `ADSP_EBADPARAM` (`adsp_err.c`'s table, index 2). `afe_callback` dispatches on `payload[1]` only and never looks at `payload[0]`, so `Recieving Rx-Enable data 0` was the kernel reading a zeroed buffer out of a rejected query. Two years of "the module says it is disabled" was the wrong reading of the same line; switching on the `pr_debug` sites is what made the difference visible. **`tinymix get TAS2560_ALGO_FF_MODULE` cannot distinguish "disabled" from "module absent" on this build — do not treat it as a protection status.**
2. **The TX feedback port starts, and it is not the blocker.** Phase 2 was the first live start of AFE port `0x1005` through the `TERT MI2S_TX Hostless` front-end — the hostless-route design works as intended, with `topology id 0x0 … ret -22` for `0x1005` exactly as stock shows. It changed nothing on the RX module: same `PL#0[0x2]`, same readback. The feedback-path config (`afe_spk_prot_prepare`, `AFE_PARAM_ID_FEEDBACK_PATH_CFG` = `0x1022C`) itself fails `ADSP_EBADPARAM` on the open port, and the familiar `Tx-Enable already enabled` line turns out to be just `tas2560-algo.c`'s else branch when that config fails — Tx-Enable was never sent.
3. **The topology is accepted by the AFE and then makes things worse.** `SET_TOPOLOGY 0x112FC` on `0x1004` was acked (`ret 0`) for the first time. With it in force, the first TAS RX set — `AFE_PARAM_ID_TAS2560_ALGO_RX_ENABLE` (`0x00012D13`) to module `0x1000FC00` — fails `ADSP_EBADPARAM`, `tas2560-send-cal`'s ioctl returns `EINVAL`, the enable is skipped and there is no get-param at all. The stock speaker topology makes the DSP reject the TAS module outright, which is what you would expect if module `0x1000FC00` is simply **not loaded**.

Taken together: neither gap the probe was built to close is the blocker. The blocker is item 1 of the static analysis — the dynamic CAPIv2 module the ADSP loads over FastRPC, which this image has no listener for. See [the FastRPC plan](#planned-next-experiment-a-minimal-fastrpc-listener) below.

### The topology cannot be undone by closing the device

The run also falsified the probe's own reversibility model, which is why the phase table above quotes "restored". That phase ran with `afe-topology-cal` long dead and no fd open, and still logged `AFE set topology id 0x112fc enable for port 0x1004 ret 0` — so it was never a baseline.

The cause is in the kernel and is unambiguous. `q6afe.c` registers `AFE_TOPOLOGY_CAL_TYPE` as `{NULL, NULL, NULL, afe_set_cal, NULL, NULL}` — **`dealloc` is NULL** — and `audio_calibration.c`'s `call_deallocs()` opens with `if (client_info_node->callbacks->dealloc == NULL) continue;`. So `audio_cal_release()` → `dealloc_all_clients()` skips it, and the same NULL makes `AUDIO_DEALLOCATE_CALIBRATION` a no-op for this cal type. **Userspace has no way to delete the block.** `afe_send_port_topology_id()` keeps sending it at every later RX port start.

What *does* work, and is now implemented as `afe-topology-cal -N`, is explicit **neutralisation**: re-SET buffer 0 on the RX path with topology `0`. Then `afe_find_cal_topo_id_by_port()` still returns the block, `afe_get_cal_topology_id()` rejects it on `if (!afe_top_info->topology)` and returns `-EINVAL`, and `afe_send_port_topology_id()` does `if (ret || !topology_id) goto done;` — no `SET_TOPOLOGY` is sent. All four of its call sites discard the return value, so the port still starts normally, and `afe_close()` clears `this_afe.topology[port_index]` so the per-port cache resets too. Neither the ioctl layer nor `cal_utils_set_cal()` validates `cal_info`, so topology 0 can be written.

Be precise about what that is and is not:

- It **is** "the kernel will send no `SET_TOPOLOGY` at the next port start", and the phase's own kernel window proves it (`topology id 0x0 … ret -22`, and no `0x112fc … ret 0`).
- It is **not** a delete — the block still exists and always will.
- It is **not** a return to the pre-topology device: the DSP was already told `0x112FC` earlier in the boot, and neutralising does not un-tell it.
- **A reboot is still the only verified way back to the pre-topology state.** Nothing measured after the topology goes in is a baseline, and the probe refuses a second run in the same boot for that reason.

This is also why the probe's phase order is fixed: everything that must be measured on an untouched device runs before the topology phase, and the phase after it is called `neutralised`, never `restored`.

### Planned next experiment: a minimal FastRPC listener

**Nothing in this section has been run. No device operation, no mount, no stock binary has been executed.** It is a plan, researched statically from the stock images and the kernel tree, recorded so the live run can be judged against what was predicted.

The 2026-09-22 run narrowed the blocker to one thing: the TAS algorithm is a *dynamic* CAPIv2 module (`capi_v2_smartAmp_TAS25xx.so.1`, ids `0x1000FC00` RX / `0x1000FD00` TX) that the ADSP loads through the FastRPC `apps_std` file service, and this initramfs runs no listener, so module `0x1000FC00` is never loaded — which is exactly what "every TAS param on `0x1004` returns `ADSP_EBADPARAM`" looks like from the AP side.

The cheapest experiment that could confirm it needs **no new binary of ours**: run stock's own `adsprpcd audiopd` from read-only mounts of the device's own partitions.

- **What stock runs.** `init.target.rc` starts `adsprpcd` (root PD) and `adsprpcd audiopd`, both as user/group `media`. `/vendor/bin/adsprpcd` is aarch64 Bionic; it dlopens `libadsp_default_listener.so`, which needs `libadsprpc.so`. The closure is `liblog`, `libcutils`, `libc++` (in `/system/lib64`, not in vendor) plus `libc`/`libm`/`libdl` and `linker64`.
- **The APEX wrinkle, and why it is not a blocker.** `system_a` is Android 10 system-as-root with **non-flattened** APEX: `linker64`, `libc`, `libm`, `libdl` are symlinks into `/apex/com.android.runtime`. `/system/apex/com.android.runtime.release.apex` stores `apex_payload.img` **uncompressed (ext4) at offset 8192**, so `losetup -r -o 8192` plus a read-only mount reaches it with no extraction and no writes.
- **Namespace shortcut.** The linker only reads `/system/etc/ld.config*.txt`. Bind-mounting just `system/bin` and `system/lib64` — deliberately *not* `etc` — gets the default search paths and side-steps the `vndk_lite` namespace rules.
- **The DSP payload.** `capi_v2_smartAmp_TAS25xx.so.1` and `tas2560_TI.bin` live in `/vendor/lib/rfsa/adsp`; the `dsp_<slot>` partition mounts at `/vendor/dsp`. `ADSP_LIBRARY_PATH` overrides the search path.
- **Open questions to settle live, before claiming any of it works.** Our kernel exposes `/dev/adsprpc-smd` but **not** `/dev/adsprpc-smd-secure`, and libadsprpc's fallback to the non-secure node is unverified. Whether `adsprpcd` needs the Android property area or `logd` present is unverified. Whether `audiopd` or the root PD is the one that matters here is unverified. And the static PD `hyp_assign`s the adsp remote heap once per boot (`staticpd_flags`), so **only a reboot resets it** — the same one-way-door property the topology block has, and it must be treated with the same care.
- **Proof hooks that do not require guessing.** `/sys/kernel/debug/adsprpc/global` and the per-fd nodes show whether a channel and PD actually came up; `busybox inotifyd` with `:r` on the rfsa directory shows whether the DSP ever *reads* the `.so` — which is the single fact that would confirm or kill the whole theory. The decisive AP-side signal is simpler still: with a listener up, the TAS RX param `0x12D13` on `0x1004` should stop returning `ADSP_EBADPARAM`.

**Proposal status (reviewed offline 2026-09-23, still not run).** The runbook, experiment script and its host test live outside the repo at `~/chef-cyclo-evidence/fastrpc-proposal-20260922/` (`SHA256SUMS.txt` verifies); they are deliberately *not* integrated here, because nothing about their runtime behaviour has been observed. The host test passes **88/88** under dash, busybox `sh` and bash (revision 3, `SHA256SUMS.txt`: `fastrpc-exp.sh` `2651969e…`, `test_fastrpc-exp.sh` `91407ecd…`, `RUNBOOK.md` `4a31dd87…`; revisions 1 and 2 are kept alongside for comparison), 12/12 mutants are caught, and the script mounts exactly the way `speaker-test-tone` does — `-t ext4 -o ro,noload`, refusing to shadow an existing mount, re-checking that the result really is read-only, and `losetup -r` for the APEX payload.

The one part worth restating, because revision 1 got it wrong, is **how you know a static PD was actually created**. Rev 1 watched for a per-process file appearing under `/sys/kernel/debug/adsprpc/`; that file is created in `fastrpc_device_open()` (`adsprpc.c:2989`, immediately after the `fl` allocation), so it only proves something opened the device. Rev 2 instead counts rows with `flags 8` in the `len|refs|raddr|flags` table of `/sys/kernel/debug/adsprpc/global` (`adsprpc.c:2764-2773`, which prints `gmaps->flags`). That is sound: `ADSP_MMAP_REMOTE_HEAP_ADDR` is 8, the only place such a map is created is `adsprpc.c:1949` inside the `FASTRPC_INIT_CREATE_STATIC` branch (1923-2005), it is guarded by `if (!me->staticpd_flags)`, and the bail path (1996-2002) resets `staticpd_flags`, `hyp_assign`s the memory back and frees the map — so a row that *persists* really does mean a static PD was created. That gate is only valid on the **first** attempt in a boot, because `staticpd_flags` latches creation to once — a retry after a successful create adds no second row, so "the count increased" would read as failure when nothing had failed. Revision 3 enforces this rather than leaving it as advice: `up` refuses with **rc 3** both when a tmpfs attempt marker shows `up` already ran in this boot and when a remote-heap (`flags 8`) map already exists before it starts, and the marker is written on success only. Retry means reboot; the runbook says explicitly not to work around rc 3, since a same-boot retry would need a different proof (a positive attach result, or a debugfs session-state change) and none is implemented or proposed.

Order of work, cheapest first: confirm the module is read at all (inotify on the rfsa dir while a tone plays — counting opens of `capi_v2_smartAmp_TAS25xx.so.1`/`tas2560_TI.bin` only, never directory scans), then whether the TAS params start being accepted, and only then think about protection actually being applied. The alternative to running stock's binary — a musl port of the BSD-licensed `quic/fastrpc` userspace — stays the real-thing option if the experiment proves the diagnosis. Whatever happens, the -20 dBFS default, the -6 dBFS ceiling and the DAC volume maximum of 15 stay until protection is both enabled *and* shown to be applying.

### tinyplay must use mmap (`-M`)

Without `-M` every play on this card XRUN-loops: live, `state: XRUN`, `hw_ptr 1024, appl_ptr 0` (also with `-p 1920 -n 8` and `-p 4800 -n 4`), a 4 s tone took 7.5–8.5 s wall-clock, dmesg showed `WARNING: at .../msm-pcm-q6-v2.c:652 msm_pcm_trigger` (a `WARN_ON_ONCE` for a pending `CMD_EOS` from the XRUN-triggered stop 40 ms after start) plus ~136 `payload size of 8` lines per run, and the tone sounded broken. Cause: `msm-pcm-q6-v2`'s copy path acks each period as soon as the DSP has copied it, so ALSA's `avail` reaches `buffer_size` immediately and the core declares an XRUN (`stop_threshold` = `buffer_size`); tinyplay then prepare/rewrites in a loop. Android's HAL sidesteps this with `stop_threshold = INT_MAX` / mmap; tinyplay only exposes `-M`. With `-M`: `state: RUNNING`, `hw_ptr` trailing `appl_ptr` by 2048 frames, 4.14 s for the 4 s tone, 0 xruns, 4 `payload size` lines, tone heard properly. **Any future ALSA client on this card must use mmap or raise `stop_threshold` to the boundary.** `speaker-test-tone` always passes `-M`; period settings stay at tinyplay's default 1024×2.

# chef-cyclo

Non-Android Linux bike-computer OS for the Motorola One Power (codename `chef`, XT1942-2, SDM636).

## Layout
- `kernel/` — Motorola kernel source `kernel-msm-MMI-QPT30.61-18` (Linux 4.4.192). Config = `arch/arm64/configs/sdm660_defconfig` + `ext_config/moto-sdm660.config` + `ext_config/moto-sdm660-chef.config`; DT = `sdm636-chef-evt.dts`.
- `stock/partitions/` — full raw dump of every partition except userdata, taken 2026-09-13 from stock QPTS30.61-18-16-19 (Android 10). `SHA256SUMS` verified against the device. Includes device-unique `persist`, `modemst1/2`, `fsg_*`, `utags`, `cid`, `hw` — do not lose.
- `stock/twrp-3.7.0_9-0-chef.img` — official TWRP, verified. `fastboot boot` it for a root adb shell (nothing flashed).
- `stock/twrp-*.txt` — kernel dmesg, cmdline, input devices and display info captured from the 4.4 kernel running under TWRP.
- `kernel-config/chef-cyclo.config` — our kernel config fragment on top of Motorola's stack.
- `initramfs/` — overlay on top of the Alpine rootfs for the boot ramdisk: `/init` (USB NCM gadget + telnet shell), inittab (telnetd, udhcpd, dbus, bluetoothd, `bt-up`), users, udhcpd and BlueZ config, `bt-up` (WCN3990 power + attach).
- `tools/btprobe.c` — libc-free helper for `/dev/btpower`, raw UART pokes, ldisc attach and an LE scan without BlueZ.
- `tools/fbtouch.c` — display + touch probe (`fbtouch info|show|bl`): holds `/dev/fb0` open, draws a test pattern through mmap + `FBIOPAN_DISPLAY`, drives `lcd-backlight`, decodes the NT36xxx multitouch stream and paints contacts; the reference for the mdss_fb userspace contract (see gotchas and the 2026-09-18 display entry). Host tests in `tools/tests/test_fbtouch.c`. Manual opt-in from the telnet shell, not in inittab.
- `tools/rmtfs/` — port of `linux-msm/rmtfs` (BSD): the EFS server the modem needs over QMI service 14, RAM-shadow writes only (`-r`), no libudev/rproc. See GPS section below.
- `tools/msmipc.{c,h}`, `tools/irsc.c`, `tools/qmuxd-lite.c`, `tools/qrtr/` — QMI/IPC-router userspace (AF_MSM_IPC adapter, IRSC gate helper, libqmi↔QMUX bridge); owned by a separate work session, see GPS section.
- `tools/servreg-locator/` — userspace SERVREG_LOC (pd-mapper) server, QMI service 0x40 instance 0x101: answers the modem's own boot-time service-registry lookup from the firmware's `*.jsn` domain descriptors. See GPS section.
- `initramfs/usr/bin/gps-up` — brings the modem up for QMI-LOC (manual opt-in for now, see GPS section).
- `scripts/` — `setup-toolchain.sh`, `env.sh` (`kmake`, `chef_defconfig`), `mkrootfs.sh` (Alpine aarch64 packages → `out/rootfs`), `mkinitramfs.sh`, `mkboot.sh`.
- `logs/` — dmesg captures from our own kernel boots.
- `toolchain/` (gitignored) — GCC 4.9, AOSP `mkbootimg`, static `apk` + Alpine keys and package cache, musl aarch64 cross compiler (GPS/QMI helpers); all fetched by `setup-toolchain.sh`.

## Device facts
- Bootloader already unlocked; A/B, active slot `_a`; no dtbo partition (DTB appended to kernel).
- Panel: Tianma 1080x2246 DSI video mode (`mdss_dsi_mot_tianma_nt_618_fhd_vid_v0`, DDIC IDs 0xDA/DB/DC = 02/61/21, `panel_ver=0x00216102`), selected by the bootloader (XBL reads the DDIC IDs, passes `mdss_mdp.panel=` on the cmdline; the DT's `qcom,dsi-pref-prim-pan` is only a no-cfg fallback). Touch: Novatek TDDI on I2C 3-0062 (driver `NVT-ts`, `NVTCapacitiveTouchScreen` = event1, IRQ gpio 67, reset gpio 66). The replacement panel fitted 2026-09-18 reports the same panel identity as the original but a different touch IC: NT36525 (trim id `0B .. .. 25 65 03`, PID `3AD9`, fw 226, 18x32 nodes, raw range **720x1600**) where the original was NT36672A (`0A .. .. 72 66 03`, PID `6005`). Both are in the driver's trim table; touch coordinates must be scaled by the evdev ABS range, never assumed to be panel pixels.
- Wi-Fi/BT MACs passed on cmdline (`androidboot.wifimacaddr`, `androidboot.btmacaddr`).
- Stock cmdline has `skip_initramfs` — strip it for our own boot image.
- No ANT+ (not enabled by Motorola). Plan: BLE via BlueZ; USB ANT stick over OTG as fallback.

## Building
```
scripts/setup-toolchain.sh   # once: fetches AOSP GCC 4.9 aarch64 into toolchain/ (gitignored)
. scripts/env.sh             # defines kmake and chef_defconfig
chef_defconfig               # sdm660_defconfig + moto-sdm660.config + moto-sdm660-chef.config -> out/kernel/.config
kmake -j$(nproc)             # Image.gz-dtb comes out in out/kernel/arch/arm64/boot/
scripts/mkrootfs.sh          # Alpine aarch64 musl/busybox/dbus/BlueZ -> out/rootfs (once, or after changing the package list)
scripts/mkinitramfs.sh       # out/rootfs + initramfs/ overlay + btprobe + BT firmware -> out/initramfs.cpio.gz
scripts/mkboot.sh            # -> out/boot.img (header values from stock boot_a.img)
fastboot boot out/boot.img   # nothing is flashed; Power+VolDown to get back to Android
```
`scripts/setup-toolchain.sh` also fetches a musl aarch64 cross compiler (Bootlin, into `toolchain/aarch64-musl/`) for the GPS/QMI userspace helpers (`tools/rmtfs/`, `tools/msmipc.c`, `tools/irsc.c`, `tools/qmuxd-lite.c`, `tools/servreg-locator/`): they need real libc (malloc, getopt, sockets, pthreads) against the rootfs's musl, unlike `btprobe`'s freestanding build with the AOSP GCC. `mkinitramfs.sh` builds all four helpers into the initramfs and fails if any source or cross-build is unavailable; it never emits `gps-up` without its RMTFS, IRSC, SERVREG-LOCATOR and QMUX dependencies.
`mkinitramfs.sh` also cross-builds `tools/fbtouch.c` (musl static) into `/usr/bin/fbtouch`.
Once booted, the phone shows up as a USB NCM ethernet device; it hands the host an address by DHCP and listens on `telnet 172.16.42.1` (root, no password). It buzzes once when `/init` starts and twice when the network is up. `bt-up` powers the WCN3990 and attaches it, bluetoothd powers it on; `bluetoothctl`, `btmgmt`, `btmon` and `hciconfig` are in the image. `fbtouch show -t 60` puts a test pattern on the panel and logs/paints touches for 60 s (`fbtouch info` for the sysfs/evdev facts, `fbtouch bl N` for the backlight).
`kmake` is `make` in `kernel/` with `O=out/kernel`, the cross prefix, and the command-line overrides a 4.4 tree needs on a modern host (`CC=` to bypass `gcc-wrapper.py`, `HOSTCFLAGS+=-fcommon`). DTB targets are relative to `arch/arm64/boot/dts` (`kmake qcom/sdm636-chef-evt.dtb`). Host deps: `libssl-dev` (for `sign-file`, since stock has `CONFIG_MODULE_SIG=y`).

## Gotchas (the short list — details in the log)
- **fastboot hangs on bulk transfers** on the ASRock B450 Steel Legend's chipset USB controller (bus 1). Use one of the four blue CPU-attached rear USB 3.1 Gen1 ports (bus 3). A hung send leaves the bootloader confused — Power+VolDown to reset.
- **`skip_initramfs` is appended by the bootloader** at runtime (with `root=/dev/mmcblk0p67 rootwait ro init=/init`); it is not in the boot image header, so it can't be stripped. Our kernel ignores it (as TWRP's does).
- **Kernel config is three fragments**, not two: `sdm660_defconfig` + `moto-sdm660.config` + `moto-sdm660-chef.config`. Missing the middle one silently drops `BOOTINFO` (build breaks in `cpuinfo.c`); the Novatek touch driver comes from the chef fragment.
- **Old tree on a new host:** `scripts/gcc-wrapper.py` is python2-only on its warning path and aborts on *any* warning → bypass with `CC=`; bundled dtc needs `-fcommon`; the Makefile's `PYTHON`/`HOSTCFLAGS` use `=` so they must be overridden on the make command line, not the environment. All in `kmake`.
- **AOSP GCC 4.9 prebuilt:** `gcc`/`g++` are python2 wrapper scripts → symlink to the UUID-named real drivers (`setup-toolchain.sh`).
- **Rootfs from Alpine without qemu:** the host's x86_64 `apk.static` populates an aarch64 root with `--arch aarch64 --usermode --no-scripts`. Skipped post-install scripts mean no busybox applet links (`/init` runs `busybox --install -s` and `busybox-extras --install -s`), no `messagebus` user (in `initramfs/etc/passwd`) and no D-Bus machine-id (`dbus-uuidgen --ensure` in `/init`). `telnetd`/`udhcpd` live in `busybox-extras`.
- **DTB targets** are relative to `arch/arm64/boot/dts`: `kmake qcom/sdm636-chef-evt.dtb`.
- **zsh doesn't word-split unquoted variables** — build scripts use `set --`/`"$@"` for lists so they work under both zsh and bash.
- **TWRP downloads** from dl.twrp.me get silently truncated; verify sha256 and resume with `curl -C -`.
- **TWRP shell scripting:** toybox `dd` wants `bs=4194304` not `4M`; `adb shell` inside `while read` eats the loop's stdin.
- **WCN3990 on a 4.4 line discipline:** no serdev, so the SoC's power-on (btpower ioctl + `c0`@2400 / `fc`@115200 pulses) and the UART reopen the pulses require happen in userspace (`bt-up`) before `btattach -P qca`; the kernel's `hci_qca` does the rest. The SoC type is taken from the DT node `compatible = "qca,wcn3990"` (the btpower node), and IBS clock votes go to the UART through the generic `TIOCPMGET`/`TIOCPMPUT` tty ioctls, which msm_serial_hs implements as its runtime-PM vote.
- **A running WCN3990 ignores the power pulses.** Its rails are shared with Wi-Fi and dropping them for <3 s does not reset it; it must be told (IBS wake + vendor pre-shutdown `01 08 fc 00` at 3.2 Mbaud) before `c0`/`fc` work again. `bt-up` does this when it restarts.
- **msm_serial_hs resets RX on every termios change** and asserts RFR on every one too, so any bytes the controller sends between two consecutive `tty_set_termios()` calls are lost. `hci_uart_set_baudrate_flow_control()` changes speed and re-enables CRTSCTS in one call, RTS last.
- **`btmgmt`/`bluetoothctl` quit early with stdin on `/dev/null`** (bt_shell reads EOF before the reply) — the way init runs things. `btprobe bdaddr` speaks mgmt directly for the one command boot needs.
- **The vendor tree's `BT_INFO`/`BT_ERR` printed pointers**: a blanket `%p`→`%pK` sed had turned `%pV` into `%pKV` in `net/bluetooth/lib.c`.
- **QMI is over `AF_MSM_IPC`, not QRTR**, on this 4.4 tree (`net/qrtr` doesn't exist; `net/ipc_router` does) — libqmi/ModemManager's QRTR/rpmsg path doesn't apply. `tools/msmipc.c` adapts the upstream `libqrtr` API onto `AF_MSM_IPC` so `tools/rmtfs/` and libqmi-side code don't need QRTR-specific ports. See the GPS handoff notes referenced from the 2026-09-15 GPS log entry for the full transport writeup.
- **A client `sendto()` on the modem's IPC-router socket blocks 30s** until a root process has run the IRSC ioctl once per boot and closed that socket (`tools/irsc.c` / `msmipc_irsc()`); `gps-up` runs it before starting `rmtfs`.
- **`AF_MSM_IPC` signals flow-control (RESUME_TX) as a 0-byte `recvfrom()`**, not a decodable packet — don't treat it as EOF or feed it to a QMI decoder.
- **`rmtfs -r` (RAM-shadow writes) is non-negotiable** until EFS writes are explicitly reviewed and approved: `gps-up` never mounts a partition read-write or writes `modemst1/2`/`fsc`/the active slot's `fsg_a`/`fsg_b` directly.
- **`fsg` is genuinely per-slot on this device — `fsg_a`/`fsg_b` only, no unsuffixed `fsg`** (confirmed against the live partition table; `modemst1`/`modemst2`/`fsc` *are* unsuffixed). An earlier version of `gps-up` assumed all of EFS was unsuffixed and deliberately never passed `rmtfs -S`; that assumption was wrong for `fsg` and would have made `rmtfs` unable to open it at all. `gps-up` now validates the active slot's `fsg_$SLOT` (exact partition, exact 10485760-byte size, from `androidboot.slot_suffix`) before exposing it, passes `rmtfs -P -r -S "$SLOT" -v`, and never inspects, links, sizes, or opens the other slot's `fsg`.
- **The modem's `msadp` debug-policy firmware file never exists**, and with `FW_LOADER_USER_HELPER_FALLBACK=y` every modem boot would otherwise stall 60s waiting for it — `gps-up` sets `/sys/class/firmware/timeout` to `1` before opening `/dev/subsys_modem` so this doesn't require a kernel config change.
- **`gps-up` is manual opt-in, not in inittab**, until a live device confirms modem PIL success and LOC service discovery under our kernel — run it by hand (`gps-up &`) from the telnet shell.
- **The display lives only while something holds `/dev/fb0` open.** mdss_fb's first `open()` unblanks, its last `close()` sets the backlight to 0 and powers the panel down (`mdss_fb_release_all`), and there is no `fb_write`: `cat > /dev/fb0`, busybox `fbsplash` or any open/draw/close tool shows nothing and then turns the screen off. The contract is open → `FBIOBLANK UNBLANK` → `mmap` → draw → `FBIOPAN_DISPLAY` → stay resident (`fbtouch.c`). No fbcon: mdss_fb has no fillrect/copyarea/imageblit.
- **A backlight write only reaches the WLED at the next frame commit.** Write `/sys/class/leds/lcd-backlight/brightness` (the mdss LED, 0–255 → 1–4095; never `leds/wled` directly), then commit a frame. After a reopen the level is otherwise parked forever: the last close saved 0 as the level to restore, the unblank restored it and blocked updates "until the first kickoff", and `mdss_fb_update_backlight()` returns early with nothing to apply, so the block is never lifted. Symptom: DSI up, panel answers `0x9C`, screen black (`leds/wled/brightness` reads 0). Android's HWC commits continuously and never notices. Live-verified 2026-09-18.
- **The touch IC is a TDDI on the panel's rails and is slaved to fb blank events**: `FBIOBLANK POWERDOWN`/`UNBLANK` through the fb core suspend/resume the NT36xxx driver (deep sleep, then bootloader reset + fw-reset wait); the last-close power-down does *not* go through the notifier, so the IC loses power while the driver still thinks it is awake, I2C fails (`CTP_I2C_READ error, ret=-3`, `/proc/nvt_fw_version` → `EAGAIN`) and the next open logs `Touch is already resume`, skips the reset, and delivers no events. Always `FBIOBLANK POWERDOWN` before the last close (`fbtouch` does). Never write `/proc/NVTflash` or any `doreflash`/`forcereflash` node: that programs the touch IC's flash.

## Goal

Boot this phone into a plain Linux userspace (no Android) and run a bike-computer UI on it. Why chef: 5000 mAh battery, full kernel source available, unlocked bootloader, good community history (LineageOS official for years). Hardware pieces that must work, roughly in order: boot → USB networking/shell → display → touch → battery/charging → BLE (sensors) → GPS → Wi-Fi → suspend/battery life. GPU stays software-rendered (Adreno needs proprietary blobs; not needed for this UI).

### 2026-09-13 (later) — initramfs and boot image

**`skip_initramfs` comes from the bootloader, not the boot image.** Neither the stock nor the TWRP boot image header has it; the runtime cmdline TWRP saw does (`… androidboot.slot_suffix=_a skip_initramfs rootwait ro init=/init …`, all appended by the bootloader, together with `root=/dev/mmcblk0p67`). TWRP still booted its ramdisk (`Trying to unpack rootfs image as initramfs…` in its dmesg) because its kernel ignores the parameter. So instead of stripping it, our kernel does the same: `init/initramfs.c` accepts `skip_initramfs` and does nothing (commit `1c67115bc` on the `chef-cyclo` branch). With an initramfs providing `/init`, the bootloader's `root=`/`init=` are ignored by the kernel.

**Config fragment.** `kernel-config/chef-cyclo.config`, appended by `chef_defconfig`: `CONFIG_DEVTMPFS(+_MOUNT)=y` (Android populates `/dev` with ueventd, stock has it off), `ANDROID_PARANOID_NETWORK` off, `LOCALVERSION=-cyclo`. Kernel is now `4.4.192-cyclo-g6d83ef138-00001-g1c67115bc`.

**USB gadget.** Stock config offers configfs functions NCM (`ncm.usb0`), Qualcomm RNDIS (`rndis_bam`), FunctionFS, MTP/PTP etc. — no plain ECM/RNDIS. NCM works with the in-kernel `cdc_ncm` driver on any Linux host, so `/init` builds a single-function NCM gadget (`1d6b:0104`, locally-administered MACs), binds it to whatever appears in `/sys/class/udc` (expected `a800000.dwc3`), gives `usb0` 172.16.42.1/24, runs `udhcpd` (leases .2–.9, no router option) and `telnetd -l /bin/sh`, then `exec`s busybox init with a small inittab that respawns both. Vibrator is `/sys/class/timed_output/vibrator/enable` (ms) — used as a display-less progress signal.

**busybox.** Alpine's `busybox-static` lacks `telnetd`/`udhcpd` (they live in a dynamic `busybox-extras`); Debian's `busybox-static` 1.37 arm64 has both plus `ip`, `mdev`, `cttyhack`, so `setup-toolchain.sh` pulls that `.deb` (`dpkg-deb --fsys-tarfile`). Initramfs is ~1 MB. `mkboot.sh` uses AOSP `mkbootimg.py` with the header values read out of `stock/partitions/boot_a.img` (v0, 4096-byte pages, offsets 0x8000/0x1000000/0xf00000/0x100, os 10.0.0 / 2021-10, stock cmdline). `unpack_bootimg` on the result matches stock field for field.

### 2026-09-16 — GPS: active-slot `fsg` fix (build/host-verified; still no live test)

Live evidence from the device's actual partition table (not assumed): there is **no unsuffixed `fsg`** partition; `modemst1`, `modemst2`, `fsc` *are* unsuffixed; `fsg_a` and `fsg_b` both exist and are each exactly 10485760 bytes; the active slot is only known from `androidboot.slot_suffix` on the cmdline; the previous/inactive slot must never be retried.

**The 2026-09-15 (night) entry's claim that EFS state was "deliberately unsuffixed" was wrong for `fsg`.** That `gps-up` looped `modemst1 modemst2 fsg fsc` as if all four were unsuffixed and explicitly avoided `rmtfs -S` to keep from ever landing on a slot-suffixed label. Since no unsuffixed `fsg` exists at all, that `gps-up` could never have actually opened `fsg` on this device — `storage_open()`'s first (unsuffixed) lookup for it was always going to miss, and without `-S` its fallback had nothing to append.

**Fix, in `gps-up`:** `modemst1`/`modemst2`/`fsc` are still exposed as plain unsuffixed `/dev/disk/by-partlabel/<name>` links (unchanged — they really are unsuffixed here). `fsg` is now handled separately by a new `resolve_fsg()`: it looks up exactly `fsg_$SLOT` for the validated active slot, requires its size to be exactly 10485760 bytes, and only then links it under its own real name (`fsg_a` or `fsg_b` — never an unsuffixed `fsg` alias, since gps-up must not fabricate a partition that doesn't exist). Any failure (partition missing, size mismatch) aborts before rmtfs starts; the other slot's `fsg` is never read, sized, linked, or tried as a fallback. `rmtfs` is now invoked `-P -r -S "$SLOT" -v` — `-S` is what lets `storage_open()`'s unsuffixed-then-suffixed lookup for `fsg` actually land on the slot this script already validated. `-r` (RAM-shadow), the read-only firmware mount, and fail-closed cleanup on any error are all unchanged.

**A real bug found while testing the fix:** `tools/rmtfs/storage.c`'s `storage_init()` only ever set `storage_use_partitions = true` (inside `if (use_partitions)`) and never reset it to `false`, and left `storage_dir` at whatever a previous call had set if the new call passed neither `storage_root` nor `use_partitions`. Harmless in production (`rmtfs`'s `main()` calls it exactly once) but a real state leak across repeated calls in the same process — it surfaced immediately when a second host test called `storage_init()` a second time in a different mode. Fixed to assign both unconditionally from the arguments on every call.

### 2026-09-16 (live, fix) — root cause found and fixed for the `EAGAIN`: a trailing newline in a sysfs write

Root-caused by reading kernel source (no phone touched) and independently re-derived by `gps-review-sonnet`: `gps-up`'s `echo /firmware/image > /sys/module/firmware_class/parameters/path` writes the string **with `echo`'s trailing `\n` included** — `kernel/params.c`'s `param_attr_store()` → `param_set_copystring()` is a bare `strcpy()` with no trimming. `drivers/base/firmware_class.c`'s `fw_get_filesystem_firmware()` then builds the direct-load path as `"%s/%s"` (search path + firmware name), so the lookup becomes `"/firmware/image\n/modem.mdt"` — a path `filp_open()` can never resolve, even though `modem.mdt` genuinely exists (confirmed offline: `debugfs -R "ls -l /image" stock/partitions/modem_a.img` shows it at 8412 bytes alongside `modem.b00`–`b28`). ### 2026-09-16 (offset fix) — RMTFS rejected every EFS sector read in that same run2 log; fixed and build-verified, not yet live-tested

Re-reading `logs/gps-fsg-live-test-2026-09-16-run2-gpsup-out.txt` in full (not just the summary above) shows `tools/rmtfs/`'s QMI handling working as designed and then failing on every single data transfer: each cycle opens `modem_fs1`/`fs2`/`fsg`/`fsc` successfully (caller ids 0–3), calls `QMI_RMTFS_ALLOC_BUFF` with `buff_size=0` and gets back `0xfd601000` (this device's RMTFS UIO region base), then issues `QMI_RMTFS_RW_IOVEC` with `phys_offset=0x200` to read sector 1 — and `[RMTFS] failed to read sector 1` every time. `grep -c "failed to read sector 1"` on that log gives exactly **115** — the same figure the entry above cites for the SMEM-crash-loop's restart count. That is unlikely to be a coincidence: this device's downstream modem firmware reports `phys_offset` as an offset *relative to* the address `rmtfs_mem_alloc()` returned, not an absolute physical address, and `tools/rmtfs/sharedmem.c`'s `rmtfs_mem_ptr()` treated it as absolute — `0x200 < rmem->address (0xfd601000)`, so every read was rejected by a bounds check, never a hardware fault. It's plausible this is what actually drove the "unrelated" crash loop above (the modem couldn't read its own EFS data and reset), but that's not confirmed here — this session did not touch the phone, so it remains a hypothesis for the next live test to check.

The same symptom, on an unrelated device (a Huawei Watch 2 LTE, MSM8909W downstream), is fixed upstream in [linux-msm/rmtfs#41](https://github.com/linux-msm/rmtfs/pull/41) ("sharedmem: accept relative buffer offsets"), open as of 2026-08-30. Its approach: auto-detect relative-vs-absolute from range (a request that fits entirely below the mapped region's size is relative; otherwise it's absolute-and-subtract, as before), with all bounds checks written as subtractions so an oversized or near-`ULONG_MAX` `phys_offset` can't wrap a `start+len` sum into a false accept the way the original code could.

**Fix, in `tools/rmtfs/sharedmem.c`**: ported the same approach as `rmtfs_mem_resolve_offset()`, replacing `rmtfs_mem_ptr()`. It takes the region's base/size instead of the opaque `struct rmtfs_mem` (so host tests can call it directly) and is shared by both `rmtfs_mem_read()`/`rmtfs_mem_write()` backends — the mmap'd-UIO path used in this live test *and* the `pread`/`pwrite` path used when `/dev/qcom_rmtfs_mem1` (rfsa) is present instead. The `pread`/`pwrite` path previously had **no bounds check at all** and, for a relative `phys_offset` like this device's, computed `phys_address - rmem->address` directly — a huge bogus offset, not merely a wrong-but-safe one; that path is fixed by the same change, even though this device currently falls back to UIO (`/dev/qcom_rmtfs_mem1` doesn't exist here — see the `failed to open` line at the top of the run2 log).

**Decision: range-based auto-detection, not a tracked alloc mode.** Considered threading a "this caller's buffer is relative" flag from `rmtfs_alloc_buf()`'s `buff_size==0` case through to `rmtfs_iovec()`, but rejected it: the QMI wire protocol carries no field saying which encoding a given `phys_offset` uses, so any such flag would be an inference on our side either way, and upstream's real-device fix already validates that inferring from range is enough. Concretely: this platform's RMTFS region sits at a multi-GB physical base (`0xfd601000`) while the mapped region itself is 2 MiB (`sdm660.dtsi`'s `qcom,rmtfs_sharedmem@0` reg is `<0x0 0x200000>`; the base observed here sits 4K past that allocation's start because of `qcom,guard-memory`), and this pairing (region size ~2000x below the base address) is guaranteed by the platform's memory map, not by anything either side of the QMI link declares — a relative offset and an absolute PA can never overlap in value here. Per-alloc mode tracking would add state with no protocol-level backing and nothing to validate it against; there is accordingly no "mode isolation between callers" test category (`rmtfs_mem_resolve_offset()` is a pure function of the values in each individual request, not of any per-caller or per-allocation state).

**`-r` (RAM-shadow) behavior is untouched** — this fix is confined to `sharedmem.c`'s address resolution; `storage.c` (which enforces `-r`) was not touched.

**Host tests**, `tools/rmtfs/tests/test_sharedmem.c` (new): relative-offset success (the exact `0x200` case from the log), absolute-address success, end-of-region boundary (last valid byte accepted, one byte past rejected, both interpretations), the `ULONG_MAX` overflow case that the old `start+len` check would have let wrap past its own upper bound, and out-of-range rejection below the mapped region. `-DRMTFS_TEST_HOOKS` additionally builds two `rmtfs_mem_read()`/`rmtfs_mem_write()` end-to-end cases (mmap-backed and `pread`/`pwrite`-backed) via test-only constructors in `sharedmem.c` that are compiled out of the production binary. All pass under `make -C tools/rmtfs test`, and clean under `-fsanitize=address,undefined` (both the new and pre-existing `tests/test-storage` suite). `make -C tools test` (`test-qmux` 388/388, `test-msmipc` 43/43, `test_gps-up.sh` 16/16) is unaffected, as expected — this change doesn't touch anything under `tools/*.c`.

**Build-verified, not live-tested this session** (no phone/flash access, per this task's scope): static aarch64 musl cross-build of `rmtfs`/`irsc`/`qmuxd-lite` succeeds; full `scripts/mkrootfs.sh` → `scripts/mkinitramfs.sh` → `scripts/mkboot.sh` rebuild succeeds; `gps-up` confirmed still absent from the packed `inittab` (manual opt-in, unchanged). Image `out/boot.img` after review fixes below, SHA-256 `b9e94a7130745621068ea2b1f2b3596c4bbd927daed4e6ef5c7f76ef84f9222c` (the pipeline's cross-compiled binaries embed build timestamps, so this differs from the pre-review hash even though `sharedmem.c`'s logic is unchanged from that build — only comments and test coverage changed; see review below). **Before promoting this**, the next live-test session should re-run the same `gps-up` CTL procedure and check whether `[RMTFS] failed to read sector 1` is gone and, if so, whether the SMEM crash loop above is gone with it or was in fact a separate issue.

### 2026-09-17 (dog timeout) — run3 confirms the offset fix, finds a new fixed +40.02s ERR_FATAL; servreg-locator implemented and build-verified

**Run3 (live, on-device): the RMTFS relative-offset fix from the previous entry works.** Every EFS iovec across 4 cycles came back `(0:0)` (zero `failed to read sector` lines, zero `iovec_fail`/`failsector`) — the modem successfully reads its own EFS (fs1 sector 1 superblock, then the whole fs1 partition) through `rmtfs` for the first time. Evidence: `logs/gps-rmtfs-offset-live-test-2026-09-16-run3-gpsup-out.txt`, `-dmesg-full.txt`, `-evidence.txt`.

**New blocker, same shape as before: the modem now dies at a fixed +40.02s after Power/Clock-ready, still with no SFR string.** Two independent research passes (`modem-timeout-opus`, live-evidence-only; `stock-modem-opus`, live stock-device comparison via adb) reached the same root cause: this is the Hexagon TMS "dog" **startup-grace timer** (`dog_hal_common.c:173:DOG detects stalled initialization`, confirmed against two public examples that show the identical 40.0×s signature, one explicitly naming the missing piece: LKML Sep-2026 "`remoteproc: qcom_common: load pd_mapper before booting the DSP`"). Root cause: **this device's AP publishes no SERVREG_LOC (a.k.a. pd-mapper, QMI service 0x40) locator**, so the modem firmware's own `servreg_locator.c` client (confirmed present by firmware strings: `SERVREG_LOC: connected to APSS Service Locator Server` / `FAILED to connect...` / `servreg_get_domainlist()`) never gets past its first lookup, and `rcinit` never finishes its init groups within the 40s the dog allows. `dump_servers` across all 4 run3 cycles shows the modem (IPC-router node 0) registering exactly two services in 40s — `0x2b` (SSCTL) and `0x42` (SERVREG_NOTIF) — never anything from DMS/NAS/WDS/**LOC (0x10)**/etc. Stock Android runs `/vendor/bin/pd-mapper` as a `class core` service, started before PIL; this project's initial design note ("no QRTR/ModemManager/pd-mapper needed") was the one assumption run3 contradicts. TFTP/RFS (service 0x1000, stock `tftp_server`) is a plausible second required daemon on this Moto firmware (it does RFS/HOB reads+writes at boot per firmware strings and stock `persist` contents) but is **not** implicated by the 40s signature itself and is explicitly out of scope for this fix — see below.

**Fix: `tools/servreg-locator/`, a from-scratch userspace SERVREG_LOC server.** Publishes QMI service `0x40` instance `0x101` (`qrtr_publish(sock, 0x40, /*version*/1, /*instance*/1)`, matching exactly what this kernel's own client — `service-locator.c`, used by `icnss` for `wlan_pd` — looks up with `LOOKUP_MASK 0xFFFFFFFF`) over the existing `tools/msmipc` transport, and answers:
- **`GET_DOMAIN_LIST` (0x21)**, the message the modem's client and this kernel's own client both send: serves domain data parsed live from `/firmware/image/*.jsn` (`modemr.jsn` → `msm/modem/root_pd`/180, `modemuw.jsn` → `msm/modem/wlan_pd`/180, `adspr.jsn`/`adspua.jsn`/etc. also indexed for when ADSP is booted; the real, confirmed-0-byte `modemus.jsn` is skipped cleanly like any other malformed file). Domain name = `soc/domain/subdomain`, service key = `provider/service`, taken directly from the descriptor rather than a compiled-in table (unlike mainline's `qcom_pd_mapper.c` fallback tables for older SoCs) — see `tools/servreg-locator/jsn.c`'s file header for the exact schema. Paginates correctly (`domain_offset`, `db_rev_count` held constant for the daemon's lifetime — a change makes both the modem's and this kernel's client loops bail with `-EAGAIN`); an unknown service name gets `SUCCESS`/`total_domains=0` with no domain-list TLV at all (not an error), matching this kernel's own client's "No matching domains found" path.
- **`INDICATION_REGISTER` (0x20)**: acked unconditionally (no live database-update stream to offer, but nothing here ever changes after startup, so that's accurate).
- **`PFR` (0x24)**, the modem's crash-report message (firmware string `SERVREG_LOC_PFR_REQ` confirmed, exact request TLV shape not independently confirmed against real hardware): best-effort decode for logging, but always acked regardless, so a wrong guess here degrades to "logged blind" rather than a hung QCCI call on the modem side.
- **Everything else** (e.g. `REGISTER_SERVICE_LIST` 0x22, which stock's own `pd-mapper` also logs as "Unsupported request"): NACKed with `result=FAILURE error=QMI_ERR_NOT_SUPPORTED` rather than left silent, so a caller's QCCI call returns immediately instead of timing out.

Wire shapes are a field-for-field port of **this tree's own kernel client** (`kernel/drivers/soc/qcom/service-locator-private.h`, `service-locator.c` — the same struct layouts this kernel already sends/expects for `wlan_pd`), cross-checked against mainline's userspace-free replacement (`drivers/remoteproc/qcom_pd_mapper.c`) for the message IDs and the PFR shape the kernel-private header doesn't have. Encoded/decoded with the same vendored `qrtr/qmi.c` (`qmi_elem_info`) codec `tools/rmtfs/` already uses for RMTFS, not a new parser. One codec caveat is patched around locally rather than in the shared file: `qmi_decode_string_elem()` writes its NUL terminator at `buf[string_len]` and allows `string_len == elem_len`, an off-by-one against a buffer sized exactly `elem_len` — every decoded string field here is declared one byte wider than the wire `elem_len` it advertises (wire behavior unchanged, see `servreg_loc.h`'s file header) so that write always lands inside the buffer.

**Integration in `gps-up`** (`initramfs/usr/bin/gps-up`): started right after `rmtfs`'s own readiness wait succeeds (needs `irsc` already run, matching `rmtfs`'s own requirement), and `gps-up` now fails closed — exactly like it already does for RMTFS — if service `0x40` (`dump_servers`: `0x00000040`) doesn't appear within a 10s bound, before `/dev/subsys_modem` is ever opened. Added to `cleanup()` and the post-boot `child_running` poll loop alongside RMTFS and the QMUX bridge, so its death is treated the same way theirs is (stop the modem safely). **No TFTP/RFS server of any kind is built, packed, or started** — `scripts/mkinitramfs.sh`'s required-source check and its file-header comment both say so explicitly, matching this fix's deliberately narrow scope (isolate the pd-mapper variable before touching a second one). `-r` RAM-shadow EFS safety is completely untouched by this change (`servreg-locator` never touches storage/`rmtfs` at all).

**Kernel: diagnostic-only SFR lookup fallback**, `pil-q6v5-mss.c`'s `log_modem_sfr()` — unrelated to the 40s fix itself, but recommended by both research passes as a cheap, always-safe way to get the *real* crash string (from this or any future modem crash) instead of "(unknown, `smem_get_entry_no_rlock` failed)": the existing `SMEM_ANY_HOST_FLAG` lookup only ever searches the SMEM **common** partition; on this firmware the SFR item may instead live in the apps↔modem **private** partition even though the modem is confirmed (firmware string: `"SFR Init: wdog or kernel error suspected."`) to pre-fill it at err-init. On a failed/empty first lookup, retries once with `to_proc=SMEM_MODEM, flags=0`. Uses `IS_ERR_OR_NULL()` on both lookups (the existing code only null-checked; `smem_get_entry_no_rlock()` can return `ERR_PTR(-EPROBE_DEFER)`), and only clears `smem_reason[0]` on whichever pointer was actually printed. No change to SSR/restart policy — `restart_modem()`'s call sequence is untouched.

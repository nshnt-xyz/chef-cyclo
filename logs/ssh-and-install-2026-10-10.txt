1. What was built

dropbear 2026.91 (Alpine) under initramfs/usr/bin/chef-sshd, respawned
from inittab, port 22 on every interface, IPv4 and IPv6. The busybox
telnetd line (inittab line 3) is byte-identical: it stays the USB-only
recovery shell. docs/features/ssh.md has the behaviour; the points
where the build differs from the spec's first sketch, with reasons:

- Authorized keys are read in place with -D /etc/chef/ssh, not copied
  into /root/.ssh: /root is an empty tmpfs that /init mounts (mode 700),
  not seeded from the image. dropbear's checkpubkeyperms (2026.91
  source) walks the file and every parent up to / and needs each owned
  by root (or the user) and not group/other writable. The staged / of
  the RAM cpio followed the builder's umask (775 under umask 002), so
  mkinitramfs.sh now sets / /etc /etc/chef 755 explicitly; the cpio and
  system_a make everything root's.
- dropbear re-executes itself (fexecve) for every connection and loads
  its host key again each time, so it gets a copy in /run/ssh and never
  opens anything under /data. The canonical key is
  /data/v1/ssh/dropbear_ed25519_host_key (dir 0700, key 0600), made on
  the phone by dropbearkey through a temp name, sync, rename, sync
  (dropbearkey 2026.91 also writes NAME.pub, removed). Corrupt or empty
  key: moved to .bad and replaced. /data not ours or failing: ephemeral
  key in /run/ssh with a kmsg line; a valid key in a root-only 0700 dir
  is still used when /data cannot be written (errors=remount-ro).
- Logging: dropbear -E into a shell read loop that writes one kmsg
  record per line ("dropbear[PID]: message", fblog shows it), at most
  20 lines per 60 s plus a suppressed count; "Pubkey auth succeeded"
  lines always pass (matched on the parsed numeric pid and date shape,
  so a username cannot fake one). A plain 2>/dev/kmsg was rejected:
  musl's unbuffered stderr writes a formatted line longer than 80 bytes
  in several write()s, i.e. several kmsg records.
- Flags: -F -E -s -m -k -T 3 -K 30 -p 22 -r /run/ssh/... -D
  /etc/chef/ssh -P /run/ssh/dropbear.pid. No -B, no -R. Remote
  forwarding off (-k); local -L kept so the host can reach loopback
  services (gpsd 2947); a key holder is root anyway.
- Packages: dropbear (530 KB installed; utmps-libs and skalibs-libs were
  already in the root) and openssh-sftp-server (199 KB) at
  /usr/lib/ssh/sftp-server, the path compiled into Alpine's dropbear.
  Modern scp uses SFTP; dropbear-scp (67 KB + dropbear-dbclient 331 KB)
  would only add legacy `scp -O`, so it is not in the image.
- Host: scripts/ssh-setup.sh (key ~/.ssh/chef-cyclo_ed25519, no
  passphrase, secrets/ssh/authorized_keys, prints an ~/.ssh/config
  snippet, never edits it), scripts/ssh-keys.py (build gates: `check` of
  the authorized_keys file, `scan` of the staged tree for private key
  material, run in mkinitramfs.sh before the cpio and in mksystem.sh),
  scripts/phone.py --ssh ADDR / PHONE_SSH (dedicated key, BatchMode,
  IdentitiesOnly, own known_hosts with HostKeyAlias chef-cyclo,
  StrictHostKeyChecking accept-new, telnet-shell PATH/HOME/bus).
  secrets/ is gitignored (.gitignore:82).
- Wi-Fi address on the panel: NetworkManager dispatcher
  30-chef-wifi-ip writes "chef Wi-Fi: <profile> IPv4 <addr>, ssh
  root@<addr>" to kmsg on wlan0 up and dhcp4-change (two lines 40 ms
  apart on a connect; left as is).

5. The first leave of the installed pair raced (my mistake), and the
   chef-storage fix it led to

Full account: B1-first-attempt-account.txt. I pushed chef-reboot and
started it detached, then ran scripts/phone-boot.sh before fastboot
appeared. 172.16.42.1 still answered, so phone-boot.sh started the old
image's fallback (`chef-storage shutdown --pause-init`). That read
mountinfo while /data was mounted; the helper's own chef-storage then
detached /data (1697.66 s); the fallback's `fuser -m /data` ran on the
now plain directory of the root filesystem and its TERM sweep hit every
process: the helper ("Terminated" at 1698.25, init resumed by its trap),
bt-up and others (respawned); its remount then failed. Nothing was lost:
chef-state shutdown (all codes 0) and the detach had completed. The same
pushed helper run again reached fastboot in 7 s.

Install-day rule (ssh_impl, agreed by ssh_review): push chef-reboot, start it with
`setsid sh -c "cd /; exec sh /run/push/chef-reboot bootloader"
</dev/null >/run/chef-reboot.out 2>&1 & true`, then a host loop on
`fastboot devices` (up to 180 s) and nothing else talking to the phone
until fastboot answers.

Fix (ssh_coord: in scope, separate commit): chef-storage shutdown
re-reads the userdata alias before each TERM and KILL sweep, checks
after fuser that the path is still a mount of the userdata device, and
otherwise redoes the same signal on the alias read next (at most 3
tries); the 2 s grace follows a TERM that ran; everything detached
meanwhile returns 0. Only the milliseconds between that check and the
kills stay unguarded. Host test: test_shutdown_path_detached_during_sweep
(fails on the old script).
